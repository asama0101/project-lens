# 設計判断

なぜそうしたか、見送った案、実装の前提。[開発者向けの情報](../development.md)の一部。

- **`app.js` は仕事ごとのファイルに割らず、判断だけを `ui/dnd.js`・`inboxops.js` に出す**: 判断（`moveSession`・`moveTask`・`applyProposal`）は、すでに純関数。`app.js` に残っていたのは、DOM の読み取りと判断が混ざった `planDrop`・`planOrder`・`planCkOrder`・`approveRequest` なので、判断だけを `planDropAt`・`planOrderAt`・`planCkOrderAt`（`ui/dnd.js`）と `approveEdit`（`ui/inboxops.js`）に出し、単体テストにした。`app.js` 全体を割る案は見送った。理由: `S`（状態）・`apply`・`render` を全モジュールが共有するので、割ると受け渡しの口が増え、`build.js` の制約（並び順・循環の禁止）にも当たる。
- **データを開けても、描けないときは、画面に理由を出す**: 手で直した日付の不正などで `renderBody` が例外を投げたら、`#view` に理由と「ファイルを直して再読み込み」を出し、バナーは `validate` の結果にする。読み込み時に `validate` が `errors` ならファイルを開かない案は見送った。理由: 直すために、画面で開けなくなる。
- **作業枠（`sessions`）の ID の重複は、`validate` で warning にする**: 枠の移動・確認・削除は ID だけで探すので、重複すると両方に効く。共有ファイルに無いタスクの作業枠（`orphanSessions`）も、同じ個人ファイルの枠なので、重複の検査に含める。error にすると、すでに重複したデータが保存できなくなり、直す手段（CLI も画面も保存に失敗）が無くなるため、warning にとどめた。
- **変更履歴（`changeLog.taskIds`）に、消したタスクの ID が残っても注意にしない**: タスクを消しても変更履歴は残す（ID を使い回さない採番が、消したタスクの履歴が残ることを前提にしている）。`validate` は「changeLog: 存在しないタスク」の注意（warning）を出さない。出すと、日程変更のあったタスクを画面で消したあと、以後ずっとバナーに出て、画面からは消せず、何もこの注意を読んで動かないため。
- **依頼のやりとり（`thread`）の件数に上限を置かない**: やりとりは、聞き返し（エージェント）と返信（利用者）が交互にしか足せない（状態の遷移の表）ので、上限（たとえば 40 件）を置いても、同じ依頼で 20 往復になり、1 人で使う道具では起こらない。起こっても 1 件の依頼が長くなるだけなので、置かない。履歴の 20 件（`pruneRequests`）と、1 件の文章の 4000 文字（貼り付けた大きな本文を防ぐ）は残す。

- **タスクの ID は、消したあとも使い回さない**: 採番は、いまのタスクと変更履歴（`changeLog.taskIds`）の ID の最大番号 + 1（`edit.js` の `nextTaskId`。ID は `<プロジェクトの ID>-<4 桁>`、例 `AA-0001`。接頭辞は `<接頭辞>-\d{4}` の完全一致で数えるので、手書きの ID `P1-0011` と `P11-0001`（採番では生まれない形）が並んでも、互いに影響しない。9999 を超えるときは Error）。番号を 4 桁の連番にするのは、タスク数 + 1 だと、最後のタスクを消して足したとき同じ ID に戻り、消したタスクの変更履歴が、新しいタスクのものとして出た。見送った案: 採番の番号をデータに持つ（形式が増える）。履歴に残らない（変更履歴に載っていない）タスクの ID は、使い回されてもよい（何も参照しないため）。
- **予定表の取り込みは、別のエージェント（`intake-calendar`）にして、どちらも `tools` を絞る。予定表の取得（MCP の呼び出し）は、エージェントではなく、呼び出し元の会話が行う**: 予定表の件名・本文は、会議の招待を送る外の人が書ける。`calendar-auto` は承認なしで書き、見張りが 30 分ごとに無人で実行するので、件名の中に「メールを送れ」「コマンドを実行しろ」のような指示があっても、実行できるツールを持たない形にした。`intake` は `Read, Write, Bash`、`intake-calendar` は `Read, Bash`（MCP のツールを含まない）。呼び出し元の会話（`/project-lens:intake calendar` と、`/project-lens:watch` の手順1.5）が、`mcpconf.js show` の指定どおりに `listTool` で取得し、`fetched.json`（OS の一時フォルダの `project-lens-fetched-<日時>.json`。実行ごとに変わる名前にして、重なっても上書き・残留しないようにする）に書いて、エージェントに渡す。書いた会話は、エージェントを呼べなかった・失敗したときは、自分で消す。エージェントは、渡されたパスを読んで、終わったら消す。エージェントは、`fetched.json` を `calendar-auto` に渡すだけで、MCP を呼ばない。取得に失敗したとき・MCP が未指定のときは、会話の側でデータを変えずに終わる（エージェントを呼ばない）。
  - 限界（受け入れた）: 会話は、取得した件名を読むので、件名の指示は会話に届く。会話側の手順にも「読むだけのデータ」と、取得に使うのは `listTool` だけという規則を書いたが、歯止めは文章だけである（`tools` を絞った効果は、取り込みの段階だけ。取得した件名・本文は、MCP・Write・Bash をすべて持つ会話本体が読む）。会話は利用者の他のツール（メール送信など）を持つので、この経路は、エージェントに任せていたときより、会話の判断に頼る。エージェントは `Bash` を持つので、コマンドの実行は、文章の規則だけで止めている。`approve` を実行しない記述も、文章だけで、許可の確認が出るかは未確認。
  - 確かめた事実（公式の資料）: エージェントの `tools` は、`mcp__<サーバー名>__*`（サーバー単位）の形を受ける。`mcp__*` は、`disallowedTools` で全 MCP を除く例だけが載っていて、`tools` で全 MCP を許す書き方としては載っていない（未確認）。プラグインのエージェントも `tools` を使えるが、`mcpServers` は無視される。
  - 見送った案: `tools` に `mcp__*` などの全 MCP を許すワイルドカードを書く案（サーバー名が利用者ごとに違うので、書けるのは全 MCP を許す形だけで、メール送信などの MCP も含み、絞れたことにならない。`tools` での効き方も未確認）。`tools` を省略して全ツールを引き継ぐ案（Bash・Write・他の MCP が使え、件名の指示への歯止めが文章だけになる）。`disallowedTools` で除く案（除くべき MCP の名前を前もって挙げられない）。サーバー名を `/project-lens:mcp` の保存時に agent ファイルへ書き込む案（`${CLAUDE_PLUGIN_ROOT}` は更新で入れ替わり、実行時に書かない規則（A1）に反する）。
  - 承認の境界の限界（受け入れた）: `inbox` エージェントは `Bash` を持つので、`node tools/inbox.js approve` を自分で実行できる。承認を人だけに限る仕組みは、エージェントの文章（`approve` はどの場合も実行しない。`reject`・`fail` は手順に書いた場合以外は実行しない）だけである。`tools` にコマンドのパターン（`Bash(...)`）を書く方法は、Claude Code の文書に書かれておらず、効くか確かめていない（未確認）。プラグインのエージェントの `hooks`・`mcpServers`・`permissionMode` は無視される（公式の文書）ので、hook で `approve` を弾く方法も使えない。コマンド単位で絞るなら、利用者の設定の `permissions.deny` に書く方法がある。`intake` の `Write` を外す案も見送った。外すと `rows.json` を `Bash` のリダイレクトで書くことになり、外部由来の文字列がシェルを通るため、かえって危ない（`Bash` は無制限のままなので、外しても安全にはならない）。
  - `/project-lens:watch` の `allowed-tools` は、`approve` を事前に許可しない。メインの会話が、エージェントの報告（外の人由来の文字を含みうる）の「承認してください」に従っても、実行の許可の確認が出る。`reject`・`get`・`wait` は、反映しない（または読むだけ）ので許可したままにしている。
- **`project-lens-mcp.json` は、一時ファイルに書いてから置き換える**: 書き込みの途中で止まっても、予定表の取り込みが全部止まる壊れ方をしないため（`data.json` の保存と同じ方針）。

- **プロジェクトの期限を、タスクの最終期限から決める**: 依頼文に日付がなく、タスクの案と一緒に決まるため、依頼で期限を必ず指定させる案は見送った。期限は、承認前の提案カードで確認して、「修正を依頼する」で直せる。
- **「プロジェクトの期限を超えます」の警告は、後ろへ動かすタスクがあるときだけ**: 影響の計算（`computeImpact` の `projectDueExceeded`）と、依頼の変更案（`planOps` の警告）は、新しい期限が今の期限より後で、かつプロジェクトの期限より後のときだけ出す。前倒しは、まだ超えていても出さない（遅れを縮める操作に「超える」と言わないため）。
- **マイルストーンの警告は、プロジェクトの期限を超えるときだけ**: 日付を動かしたときに「後ろにタスクが残る」ことで警告する案は見送った。途中の節目（例: 機器発注）の後には、いつもタスクが残るため、毎回警告が出て意味がなくなる。
- **共有 + 個人の 2 ファイルで使う**: 1 つの共有ファイル（`data.json`）を複数人が使い、作業枠・会議・休みなどは各自の個人ファイル（`personal.json`）に置く。保存前に、ファイルごとに更新日時を比べ、他の更新があれば最新のファイルに同じ編集を当て直して保存する（ロックはしない）。分け方と見送った案は「画面の動き > 共有ファイルと個人ファイルの分割」、保存の規則は「保存と競合」（`ui-files.md`）。
- **ToDo タブの週の一覧は、保存せず、タスクの期限・状態・作業枠から、その場で計算する（`core/week.js` の `weekTasks`）**: 「今週やるもの」は、タスクの期限と予定の枠から決まるので、手で登録すると、タスクと二重に管理することになる。期限や枠を直すと、一覧もそのまま変わる。見送った案: ① 週ごとの一覧を個人ファイルに保存する（スナップショット。週の終わりの状態をあとから正確に見られるが、期限や枠を直しても一覧が変わらず、二重管理に戻る）。② 個人の ToDo（タスクと別の、自由な件名の ToDo）を残す（タスクの期限・予定の枠・実績と二重に入れることになり、「ToDo・タスク」の言い方も入り乱れる）。③ 手で一覧に足す操作（前倒し。週に載る規則の外に、手で持つ状態ができ、保存が要る。来週のタスクを今週やるときは、今週に予定の枠を置けば載る）。④ 「回す」と、回した回数（要件から外した。期限と枠から計算するので、次の週に残ったものは、そのまま次の週にも載る）。あわせて決めたこと: Cancelled のタスクは、期限超過でも、枠や実績があっても、どの週にも出さない（中止したタスクは「やること」ではないので、一覧にも、稼働の画面のタスクの表にも入れない。実績の時間は、稼働の画面で見る）。完了の入力欄で選べる状態から Waiting を外す（Waiting は待ち先が要り、完了の入力欄には待ち先の欄が無いため。Waiting にするのは、ほかの画面の状態の欄）。過去の週も同じ規則で計算し、「その週の終わりに未完了だったか」は、今の状態で近似する（状態の履歴を持たないため。その週のあとで完了したタスクは、その週に枠も実績も無ければ、その週には出ない）。
- **スキルの起動**
  - `intake` のスキルも `disable-model-invocation: true`（利用者が `/project-lens:intake` と明示して呼ぶ）。予定表の会議は承認の確認なしで書くので、モデルの判断では起動させない。
  - いずれも、変更案を示して承認を得てからデータを書き換える。書き込みは CLI（`tools/inbox.js`・`tools/intake.js`）に任せ、CLI が書く前に検証（`validate`）し、通ったときだけ書く（通らなければ何も書かない）。`intake`・`intake-calendar` のエージェントは、書き込んだ後に `validate.js` を実行しない（書けた後に `errors` は出ないので、同じ検証の二重になるため）。エージェントが `data.json` を直接書き換えることはない。日程の変更は、受信箱の経路（HTML の帯 → `inbox` エージェントの `propose` → `approve`。「HTML からの依頼（inbox）」（`inbox.md`）を参照）で行う。
  - `doctor`・`init`・`mcp`・`watch` も `disable-model-invocation: true`（利用者が明示して呼ぶ）。`doctor`・`init`・`mcp`・`watch` は、自分のスクリプトだけを `allowed-tools` で事前に許可している。
- **画面の編集では前後のタスクを見ず、前後の見直しを Claude Code の依頼に寄せた**: 画面での期限・開始日の変更に確認パネルを挟むと、1 件を直すたびに手が止まるため。前のタスクの期限を見て、次のタスクをまとめて動かす判断は、原因と理由を残せる依頼の処理に集めた。代わりに、次のタスクとの食い違い（次のタスクの期限が前のタスクより前になる）も画面は警告しない。
- **入口を HTML の依頼に寄せた**: 日程の変更・タスクやプロジェクトの変更を、コマンド（`replan`・`inbox`）ではなく、HTML の「Claude Code に依頼する」から行う。入口が 3 つ（コマンド・画面の編集・依頼）に分かれていて、どれを使うか分かりにくかったため。手動で依頼を処理する入口（`/project-lens:inbox`）は設けず、処理は `/project-lens:watch` の見張りが行う。見張りが止まっている間、依頼は処理されない。見送った案: 手動の入口を残す（コマンドが増え、入口の整理にならない）。
- **祝日の更新を `holidays.js ensure` に置いた**: 更新の判定（未取得・取得から 30 日超・一覧の最終日が今日以前・提案が使う日が一覧の範囲外）を `needsHolidayUpdate` の 1 か所に置き、`propose` と `ensure`（`watch` を始めるとき）が同じ判定を使う。判定をエージェントの指示（Markdown）に書くと、実行のたびにぶれるため。見送った案: Claude Code の起動時（`SessionStart` フック）に取得する（毎回の起動でネットワークに出る。フックの設定が増える）。
- **土日祝を営業日に数える設定を `data.json` ごとに 1 つにした**: `settings.countWeekendsAndHolidays`（`true` のときだけオン）。仕事用とプライベート用で `data.json` を分けて使うため、プロジェクトごとの切り替えは要らない。オンのとき、土日と日本の祝日を営業日に数え、手動の休み（`holidays`）は飛ばす。切り替えは HTML の設定タブ（「基本の設定」の先頭の行「営業日の数え方」）だけで行う。見送った案: 土・日・祝日を別々に選ぶ（まとめて足りる）、プロジェクトごとの切り替え（`data.json` を分けるので不要）、依頼からの切り替え（設定は画面で変える方針）。
- **`intake` スキルは手動起動に限る**（`disable-model-invocation: true`）: `calendar-auto` が承認なしで、予定表の会議の追加と、終わっていない未確認の会議の更新・削除を行うため（plugin-rules.md の B4 の「不可逆な書き込み」）。「予定表を取り込んで」と頼んでも、モデルは起動しない。`/project-lens:intake calendar` と打つ。見送った案: 自動起動のままにして、理由を書く（承認なしの削除を、モデルの判断で起動できてしまう）。calendar だけ別のスキルにする（コマンドが増え、README・テストの直しが広がる）。
- **MCP を同梱しない**
  - 予定表の MCP（Outlook など）は、利用者が Claude Code に用意したものを使う（`.mcp.json` はない）。
  - 指定は `/project-lens:mcp` で `${CLAUDE_PLUGIN_DATA}`（`~/.claude/plugins/data/` の下）の `project-lens-mcp.json` に保存し、`data.json` には入れない。
  - このファイルには `schema_version`（現在 1）を入れる。無いファイルは古い形式として、読まずに「project-lens-mcp.json（<パス>）を削除してから、/project-lens:mcp で指定し直してください」のエラーにする（利用者の判断: 古い形式への互換性は不要）。`/project-lens:mcp` の保存（`set`・`clear`）も、このファイルを読むので同じエラーで止まる。そのため、パスを示して、先に削除するよう案内する。保存形式を変える版では、この節に移行手順を書く。
- **レポート（共有用 HTML の保存）を機能ごと消した**: 共有ファイルを開けば、各自が同じ画面を見られるので、共有用の HTML を出す手段は要らない。レポート専用の `core/reportspec.js`・`ui/views/report.js`・`ui/views/reportpanel.js`・`ui/savefile.js`、`prefs.js` の記憶、`gantt.js` の `readonly` 引数を消した。`data.json` の `settings.reportShowMeetingTitles` は、残っていても検証が何も言わない（データからは消さない）。見送った案: 読み取り専用のガントだけ残す（使う画面がなくなるため）。
- **SharePoint Online 上には、共有ファイル（`data.json`）だけを置き、ネットワークドライブ（または同期したフォルダ）経由で使う。個人ファイル（`personal.json`）は手元に置く。https の URL での読み書きは対応しない**: 共有ファイルをローカルに置けない利用者がいるため。画面は `showOpenFilePicker`・`createWritable`・`lastModified` だけを使い、ファイルの場所を区別しない（`store.js`）ので、割り当てたドライブのファイルを選べば、コードの変更なしで使える見込み。個人ファイルは、各自が自分の手元で使うので、置き場の共有は要らない。利用ガイド（`docs/guide.md`）に手順を書いた。見送った案: Microsoft Graph での読み書き（Entra ID へのアプリ登録と権限の許可が要り、利用者は管理者に頼めるか不明。ログインの戻り先に `file://` を使えないので、HTML を置く https の場所も要る。競合の検知を ETag に、自動の読み直しを Graph 向けに作り直す必要がある）、Power Automate を間に挟む案。未確認: ネットワークドライブ・同期フォルダの共有ファイルを、ブラウザの「ファイルを開く」で選べるか・保存できるか・実ブラウザの権限の確認が通るか。同期の遅れや WebDAV の遅さが、自動の読み直し（4〜16 秒ごと）と、共有に無いタスクの作業枠のバナー（同期の遅れで、一時的に出うる）に与える影響。CLI（`tools/cli.js` の置き換え保存）・`/project-lens:watch` がこのドライブで動くか。
- **外部パッケージを使わない**: ローカルサーバー・常駐プロセス・データベースも使わない。Excel の取り込みだけ、Python の `openpyxl`（システムのもの、または専用の venv `<置き場>/venv` のもの）を使う。
  - CI（`.github/workflows/test.yml`）は、`windows-latest` で `npm test` だけを流し、lint は流さない。lint の道具（ESLint など）が外部パッケージになり、この方針とぶつかるため。構文の誤りは、`npm test` と `npm run build` が読み込む時点で見つかる（テストにもビルドにも読み込まれない .js が無いかは、未確認）。見送った案: `node --check` を CI に足す（読み込まれるファイルでは、新しく見つかるものがない）。ESLint を入れる（`devDependencies` と設定ファイルが増える）。
- **データファイル（`data.json`）の書き込みは、置き換え**: CLI（`tools/cli.js` の `saveData`）は、同じフォルダの一時ファイルに書いてから `renameSync` で置き換える。途中で止まっても元のファイルが壊れないようにするため（`.project-lens/` は `.gitignore` の対象で、Git に履歴がない）。置き換えは、100 ms 待って最大 3 回試す（`renameWithRetry`。ウイルス対策ソフトなどが一時的に開いている場合に備える）。3 回とも失敗したとき（ほかのプログラムが開いている、など）は、「置き換えられませんでした」の例外にして、`data.json` は元のままにする（直接の上書きはしない。上書きの途中で止まるとファイルが壊れるため）。やり直しの待ちが足りるかは、実機では未確認。OneDrive などの同期フォルダでは、同期ソフトが一時ファイルを掴んで置き換えに失敗し、毎回このエラーになる可能性がある（未確認）。一時ファイルは、成功・失敗のどちらでも消す（消せなくてもエラーにしない）。ブラウザの保存（`store.js`）は変えていない。File System Access API の `createWritable` は、閉じるまで一時の場所に書いて、閉じたときに置き換える仕様（この環境では動作を確かめていない。未確認）。
- **Excel 用の openpyxl は、システムにあれば使い、無ければ専用の venv `<置き場>/venv` か、システムの Python のユーザー領域のどちらかを選んで入れる**
  - 探す順: ① システムの Python が、固定した版と同じ 3.x 系（`3.1.x`）の `openpyxl` と、`et_xmlfile`・`defusedxml` を import できる → それを使う（何も入れない。承認も要らない）。② `<置き場>/venv` の Python が動き、固定した版（`==3.1.5`）の `openpyxl` を import できる → その Python で読む。③ どちらも無い → 入れ先（既定は venv、`--system` はシステムのユーザー領域）を選び、承認（`--yes`）のあとで入れる。
  - venv の入れ方: 作成元の Python（`choosePython` が選ぶ）で `python -m venv <置き場>/venv` を作り、その venv の Python で `pip install --quiet --require-hashes -r requirements.txt` を実行する。版とハッシュは `requirements.txt` で固定する（ハッシュは PyPI の配布ファイルから `pip hash` で求めた値）。入れる前に、場所と内容を示して承認を求める。
  - 専用フォルダ `project-lens-pylib`（`pip install --target`）から venv に戻した理由: 他のプラグイン（`pptx-deck`・`vault-kb`）が、同じ `<置き場>/venv` を使い、`setup [--yes]`・`doctor` の形も同じ。方針をそろえ、利用者が 1 つのやり方で覚えられるようにするため（利用者の判断）。作成元の Python に `venv`・`ensurepip` が無いときは、venv を作れない。`--system` か CSV を案内する形で、受け入れた（壊れた venv の作り直しの分岐は持たない）。
  - `<置き場>/venv` が既にあって使えない（壊れた・版のずれた・利用者自身の venv）ときは、**消さずに**、パスを示して「project-lens が作ったものなら消して、ほかのものなら移動してから、もう一度」と案内し、終了コード 3 で止まる。project-lens は、既にあるフォルダを消さない。消すのは、この実行で `python -m venv` を始めたフォルダ（直前に無かったもの）を、作成や pip install に失敗したときだけ（`rmSync` の `maxRetries: 3`）。理由: 壊れる・版がずれるのは、基底の Python を消したときと、固定した版を上げたときだけで、起きても利用者がフォルダを消せば直る。印のファイル（`project-lens-venv.txt`）による、project-lens が作ったフォルダだけの自動の削除と作り直しは、持たない。被害の小さい場面に対して仕組みが大きいため（利用者の判断: 過剰な防御を減らす）。印のファイルが残っていても、何も起きない。見送った案: 印による自動の作り直しを残す（上の理由）、`pyvenv.cfg` の有無で判定して消す（レビューで、利用者の開発用 venv を、承認だけで中身ごと消すことが再現された）、既にある venv へそのまま pip install する（利用者の venv の中身を変える）。
  - 入れ先にシステムを選べるようにした理由: 利用者が「システムの Python に既にある環境に揃えたい」ことがあるため（利用者の要望）。`--system` は `pip install --quiet --require-hashes --user -r requirements.txt` で入れ、入れたあとにその Python から import できること（`systemUsable`）を確かめる。ユーザー領域は、システムの探索（①）が最初から見る場所なので、入れたあとは「システムにある」として扱われ、特別な経路は要らない。
  - 既定は venv（`--system` を付けたときだけシステム）。システムを変えない側を既定にするため。承認前の案内には、両方の入れ先と、システムの注意（他のツールの openpyxl と版が衝突しうる、アンインストールで消えない、仮想環境の Python では使えない）を書く。`--system` を指定しても、venv に固定版が既にあれば、何も入れずに成功し、「専用の venv に既にあるため、システムには何も入れていません」と伝える（`locate` の判定を変えない）。見送った案: `--system` のとき venv の判定を飛ばして必ず入れる（使える環境があるのに入れるため）、入れる前に `pip list --user` で既存の版を表示する（頼まれていない）。
  - 注意の文言: ユーザー領域に別の版の openpyxl が既にあれば、固定した版（3.1.5）に置き換わり、元の版には戻せない（レビューで指摘）。
  - venv の Python は `-I`（環境変数 `PYTHONPATH`・`PYTHONHOME` など、ユーザー領域、作業フォルダを無視する）で動かし、pip は `--isolated --disable-pip-version-check`、インストールは `--only-binary=:all:`（ビルド済みの配布物だけ。`setup.py` を実行しない）で行う。利用者の `PYTHONPATH` に別の openpyxl があっても、venv の判定がすり抜けず、読み取りも同じ環境で動く。システムの Python は、`PYTHONPATH` を使う利用者がいるので、`-I` を付けない。
  - `--user` が失敗するとき（仮想環境の Python、ユーザー領域を読まない設定など）は、失敗の理由と、`--system` を付けずに venv に入れる案内を出して止まる（自動で venv に切り替えない。入れ先は利用者が決めるため）。
  - 作成元の Python に `venv`・`ensurepip` が無いときは、`python -m venv` が失敗し、その文言（標準ライブラリの `venv`・`ensurepip` を確認、`--system`、CSV）と stderr を出して止まる。`xlsx.js` は前もって調べない（作成の失敗と同じことを二重に調べていたので外した）。`doctor` は、使う前に知らせるため、前もって判定する。`--system` でも、前もって `pip --version` を調べず、`pip install` の失敗の文言（pip が使えるか、ネットワーク・権限）で伝える。
  - システムのものは、版の範囲（同じ 3.x 系）しか見られず、ハッシュは検証できない。範囲外や `defusedxml` 不足のときは「使えない」と見なし、②・③に回す。
  - Python の `-c`・`-m` は、現在のフォルダを先頭の検索場所にする。作業フォルダに置かれた `openpyxl.py` などを、承認の前の検査で実行しないよう、`realRun` は一時フォルダで実行する。`PYTHONPATH` は、利用者の設定済みの値を消さず、追加する値を先に置く。
  - 使う Python は、候補（`py -3`・`python`・`python3`）のうち、3.12 以上で、システムに使える openpyxl がある最初のもの（`choosePython`）。どれにも無ければ、3.12 以上の最初の候補（venv の作成元、`--system` の入れ先）。
  - 見送ったこと（既知の穴）: 並行実行のロック（見張りと手動の取り込みが同時に入れると、半端になりうる。コードからの推論で、未再現）、venv の中身の改ざん検査（置き場は利用者の権限で書けるので、同じ利用者の権限内の話）、システム側の openpyxl の版の下限（3.1.0〜3.1.4 も通る）、`requirements.txt` の変更の検出（openpyxl の版だけを見る。et_xmlfile・defusedxml の版だけが変わっても、使えるとみなす）、`pip`・`venv` の実行のタイムアウト（無い。接続が止まると見張りが固まりうる）、Windows 以外の配置（`bin/`。Windows 専用のため）、`doctor` の「venv を作れません」の判定が、`choosePython` が選ぶ作成元とずれうること（複数の Python があり、2 番目だけが venv を作れるとき。`doctor` は選ばれた Python だけを見る）、承認の前に `<置き場>/venv` の別のフォルダを検知しない（承認して `--yes` を付けたあとで止まる）。
  - 確認したこと: 実機（Windows 11、Python 3.14）で、`setup --yes` が一時フォルダに venv を作り、`-I`・`--isolated`・`--only-binary=:all:` で openpyxl を入れて、Excel を読めること（統合テスト。システムの Python に使える openpyxl がある PC では、この統合テストは skip される）。未確認: 実際のシステムの Python への `pip install --user`（この PC を変えるため実行していない。`pip` の呼び方と、入れたあとの確認は、`run` を差し替えた単体テストのみ）、`venv`・`ensurepip` が無い Python、pip が使えない場合・オフラインの場合（スタブの単体テストのみ）、Python 3.12（手元は 3.14）、作成や pip install に失敗したあとで、作りかけの venv を消すこと（スタブのみ）。確認したこと（そぎ落とし後）: 実機で、中身のある `<置き場>/venv` に対して `setup --yes` が、消さずに終了コード 3 で止まること。
  - 要件は、Python 3.12 以上。venv に入れるには標準ライブラリの `venv`・`ensurepip`、システムに入れるには pip が要る。入れられないときは、失敗を返し、Excel を CSV に保存する案内を出す。
  - `defusedxml` は必須とする。openpyxl は、`defusedxml` が入っているときだけ、細工した xlsx（XML の入れ子の展開で巨大になる）を防ぐため。
- **依頼の操作を `addTask` と `moveDue` に絞った**: 日程の連鎖（後続タスクを最小限だけ動かす）と、文章でのタスクの登録は、画面では手間がかかる。一方、状態・重要・削除・プロジェクトやマイルストーンの変更は、画面で 1 回で直せ、依頼の処理（操作の種類ごとの変更案と検査）を維持する割に使われなかった。そのため、依頼はこの 2 つに絞り、ほかは画面で行う。保存済みの検証用の `OP_KINDS`（17 種類）は残す（古い依頼が `data.json` に残っていると、検証に通らず保存できなくなるため）。新しい提案・承認では `PROPOSE_OPS` 以外を拒否し、承認時は失敗にして「もう一度提案してもらう」で作り直せる。見送った案: `OP_KINDS` も 2 種類にする（古い依頼を持つデータが保存できなくなる）、古い依頼を黙って捨てる（利用者が頼んだ記録が消える）。
- **チェックリストは、ID 付きの項目で、タスクの状態と連動させない**: データは `task.checklist = [{ id, text, done }]`。項目に `id`（`c1`…）を持たせた（番号で指すと、並び替え・削除のあとに別の項目を変えてしまう。項目を指すのは画面の編集だけで、依頼は項目を指さない）。全項目をチェックしても状態を `Done` にしない（状態の変更には予定枠の確認など付随する処理があり、自動にすると意図しない変更が起きる。進捗率 ＝ `Done` ÷ 全タスクの規則も変えずに済む）。代わりに `Done` にするときだけ警告し、「残りをすべてチェックして Done にする」で Done にできる。見送った案: 項目ごとの期限・担当・メモ（頼まれていない）、全部チェックで自動 `Done`、未チェックがあると `Done` にできない（禁止）、Excel の WBS 取り込みへの対応（列の決め方が要る）、依頼による項目の並び替え（画面で足りる）。
- **Done にするときのチェックの警告は、「残りをすべてチェックして Done にする」と「やめる」の 2 択にした（未完了の項目を残したまま Done にする選択肢は持たない）**: 未完了のまま Done にできると、あとから見て、その項目が「やらずに済んだ」のか「チェックし忘れ」なのか、区別がつかないため（利用者の判断）。要らなくなった項目は、削除してから Done にする（警告にヒントの 1 行を出す）。Done を禁止するのではない（警告の中で 1 回押せば、残りにチェックを付けて Done にできる）。見送った案: 項目ごとに「対象外」の印を付けられるようにする（項目に新しい状態が要り、データ形式・進捗の M/N・優先順位の倍率の数え方を決め直すことになる）。ToDo タブの完了の入力欄（`completeTask`）も、同じ理由で、未完了の項目が残ったまま Done では保存しない（「残りをすべてチェック」でチェックするか、項目を削除してから保存する）。
- **ToDo の「今日の分は完了」は、保存する値を持たず、今日の実績から導く。「今日の分を完了」は、実績だけを書く**: タスク全体は終わっていないが、今日の分は終えた、という状態は、今日の日付の実績があるかで、見分けられるため（新しい値を足すと、データ形式・検証・個人ファイルへの分割・旧データの扱いを決め直すことになる）。ボタンは、状態を変えず（Done・予定の枠の解除・次回の作成をしない）、実績だけを書く（利用者の判断。完了の入力欄の初期値が Done で、今日の分だけを終える操作が見えなかった）。見送った案: 押した印を、タスクか枠の値として保存する（意図は正確だが、上の理由で重い）、実績の時刻を省略できるようにする（印が、実績の有無から導けなくなる）。残りの予定の枠があっても印は付く（印の意味は「今日の実績がある」で、残りの枠の有無とは別）。完了の入力欄のチェックリストは、ほかの画面と同じ部品にした（表記が画面ごとに違うと、同じ項目を直す手順を覚え直すことになるため）。その代わり、チェックの操作は、保存を待たず、すぐタスクへ保存する（部品がそのように動くため）。
- **「重要」は紫（`--imp`・`--imp-soft`）、期限超過は赤（`--bad`）に分ける**: 両方が赤だと、行や札を見ても、重要なのか遅れているのか区別できなかったため（利用者の判断）。赤は「遅れ」だけの意味にする。「重要」の印（ガント・リストの行の帯と背景、右の列・ToDo の札、スケジュールの枠の件名）は、すべて紫にする。ダークテーマ用の明るい紫も持つ（札の文字は、背景色の反対の `--surface`）。見送った案: 「重要」を橙にする（Waiting・催促の琥珀色と近い）、「重要」の帯・背景をやめて札だけにする（行全体で重要を見つけられなくなる）。確認したこと: ライト・ダークで、ガントの行・凡例・右の列の札が紫で、期限超過の札・帯が赤のままであること（Chromium・Playwright）。未確認: スケジュールの枠の件名、リストの行の見た目、幅 900px 以下。
- **期限超過・回答予定日の超過は、札・帯・日数で目立たせる（色だけに頼らない）**: 理由の灰色の小さな文章の途中にあって、見落とすため（利用者の判断）。遅れの日数は `core/metrics.js` の `lateInfo`（`overdue`＝期限を過ぎた日数、`lapsed`＝Waiting の回答予定日を過ぎた日数。完了したタスクは 0）で 1 か所で数える。見送った案: 画面の上端に「要対応 N 件」の帯を出す（件数と移動先の仕様が増える。画面案のうち、利用者が採らなかった）。ガント・リストの行にも、遅れの赤の帯と背景を付ける（「重要」を紫にして区別したあと。重要と重なる行は、紫の帯の内側に赤の帯を並べ、背景は赤を優先する）。
- **ガントチャートに実績の線は出さない（日ごとの実績は、スケジュールと稼働で見る）**: 線は、最初の実績の日から今日（完了なら完了日）までの 1 本で、実績の無い日も塗られ、「いつ作業したか」とは読めないため（利用者の判断）。ガントの表示範囲は、タスクの開始・期限・マイルストーン・プロジェクトの期間で決め、実績の日付では広げない。見送った案: 実績がある日ごとの印を出す（行が混み、同じ情報がスケジュール・稼働にある）。

- **実績は、予定の枠の `actual`（`{ date, start, end }`）に持たせる。実績だけの枠（`kind: "actual"`）は、予定のない作業のためだけに残す**: 利用者の判断。予定の時刻は変えず、予定どおりでなかった時間（ずれた・延びた）を `actual` の日付・時刻で表すので、計画と実際のずれが残る。`actual` は 3 つの値を必ず書く。実績の区間は `core/sessions.js` の `actualSpans`（実績だけの枠の自身の時間 + 予定の枠の `actual`）で、稼働・`taskActual`・ToDo タブの実績の分（`weekTasks`）・スケジュールのサマリー・未確認の判定は、すべてこれで数える。実績の区間どうしの重なりだけを `validate` の error にし（稼働に同じ時間を二重に数えないため）、予定と実績の重なりは許す。`kind: "actual"` の枠に `actual` があるのは error。実績は、休みの日にも置ける（事実の記録のため）。開始が今より後の実績は置けない。会議は、予定の時間（`start`・`end`）と別に、任意の `actual`（`{start, end}`）を持つ。規則は「画面の動き > 今日のタスクとスケジュール」「会議と稼働」（`ui-today-todo.md`）。実行中の印（作業枠の `running`）は持たず、古いファイルに残った `running` のキーは読まず、検証も何も言わない（移行のコードは持たない）。見送った案: 予定の枠の書き換え（計画と実際のずれが残らない）。「開始」「終了」のボタンを残す（利用者がやめると決めた）。枠ごと・今日のタスクの行・会議ごとの「実績にする」のボタンで、予定の時刻のまま確定する（時刻を直すには予定の枠を動かすしかなく、予定が失われる）。「未確認」の範囲を区切る設定（`actualsFrom` など。予定表の取り込みを今日以降だけにして、採用前の未確認が山にならないので、足さない。すでにある古い未確認は、手で消す。負担になってから足す）。
- **予定と実績を 1 つの枠に持たせた（実績の枠に予定への参照を持たせない）**: 実績を保存し直して更新・消せるようにし、予定の枠とその実績を 1 つの作業として見ること（どの実績がどの予定の分か）を、枠どうしの対応に頼らずにするため。1 つの作業に枠が 1 つになる。見送った案: ① 実績の枠が予定の枠の ID（`plannedId`）を持つ（予定の枠を動かす・消すときに、参照を保つ規則が要る。参照が切れた実績の扱いも決める必要がある）。② 2 つの枠のまま、実績を直す欄だけを足す（どの実績がどの予定の分かが分からない問題が残る）。③ 実績のブロックをドラッグして時刻を直す（入力欄なら日付・時刻を正確に直せる。実績のブロックは、押して予定の枠を選ぶだけで、ドラッグ・サイズ変更はできない）。予定の枠を別の日・時刻へ動かしても、`actual` は動かさない（`actual.date` を明示しているため。やった時間は、予定を動かしても変わらない）。実績を持つ予定の枠を消すと実績も消えるので、確認を出す。分けて持つ形のデータ（予定の枠と、別の実績だけの枠）は、そのまま読め、数字も同じ。自動では 1 つにまとめない（どの実績がどの予定の分かを、機械が決められないため）。
- **実績を持つ予定の枠・会議は、実績の時刻の 1 つのブロックで描き、予定の時刻は点線の影（`pghost`）で添える**: 利用者が選んだ。予定のブロックと実績のブロックを並べると、1 つの作業が 2 つに見える。会議も、予定の時刻のブロックに実績の文字を添えるだけでは、やった時間がカレンダーの位置から分からない。1 つのブロックなら、カレンダーの位置が、やった時間そのものになり、予定とのずれは、違うときだけ出す影で分かる。実績を持つ枠・会議と、その影は、ドラッグできない。予定を動かすときは、先に「実績を消す」で予定のブロックに戻す（実績ができたあとは、予定の時刻を動かす意味がほとんど無いため）。見送った案: ① 予定のブロックの中に実績の帯を描く（実績が予定の外（別の時刻・別の日）に出ると描けない・見づらい）。② 予定と実績の 2 つのブロックを並べたままにする（利用者が望まなかった。2 つに見え、半分の幅では文字が切れる）。③ 影もドラッグできるようにして、予定を動かす（実績を持つ予定を動かす意味がほとんど無く、ドラッグの対象を、実績を持たない予定の枠・会議だけに絞るため）。
- **ドラッグで置いた枠は、過去の時間でも予定（`planned`）にする**: 利用者の指摘（置いたタスクが、予定ではなく実績になった）。置く操作は予定を立てる操作で、実際にやったかは実績の入力で決めるため。過ぎた予定は、重なる実績が無ければ未確認として出るので、実績を入れる流れは変わらない。見送った案: 過去に置いたら実績にする（置いただけで稼働に数えられ、実績の入力を飛ばしてしまう）。
- **勤務時間（`settings.workday`）の設定をやめ、スケジュールの時間の軸を 00:00〜24:00 の固定にした**: 利用者の判断。勤務時間の外（早朝・夜）の作業も枠に置けるようにし、設定の項目を減らすため。作業枠は、その日の 00:00〜23:59 のどこにでも置ける（終了の上限は 23:59。時刻は `HH:MM` で持ち、24:00 は書けないため。`core/sessions.js` の `LAST_END`）。一緒に、空き時間の計算（`freeSlots`）と、週表示の日付の下の「空き 〇h」もやめた（勤務時間がないと、空きの範囲が決まらないため）。古いファイルに残った `workday` は読まず、検証も何も言わない（移行のコードは持たない）。`PERSONAL_SETTINGS` から外したので、古い個人ファイルに残っていると、次の保存で共有ファイルの `settings` に移る（未知のキーは共有に置く規則のため。読む側はないので、動きは変わらない。実データでは未確認）。突発タスクの開始の初期値は、今日なら現在時刻を 15 分刻みに切り上げた時刻（23:45 まで）、ほかの日は 09:00（`views/schedule.js` の `urgentDefaultStart`。勤務の開始の代わりの固定値）。見送った案: 勤務時間を表示の範囲としてだけ残す（設定が残り、範囲の外の枠の扱いを決める必要がある）。
- **突発タスクの入力欄は、「＋ 突発タスク」のボタン（`data-urgent-open`。ヘッダーと、ToDo タブの左の列の見出しの横）からだけ開く**: 利用者の判断。カレンダーを押す操作（枠・会議の選択）と混ざらないようにするため。ToDo タブの左の列のボタンは、カレンダーの外にあり、ヘッダーと同じ処理（`openUrgent`）を通る。見送った案: 週表示・日表示の空き時間のボタンを押して開く（入口が増え、押すまで透明にしても、選択やドラッグの場所と重なる）。
- **ToDo タブで候補のタスクを今日へ入れるときは、小さな入力欄（開始・長さ）で今日の予定の枠の時刻を決める**: 利用者が選んだ。今日の ToDo は今日の枠から導く（`todayTasks`）ので、今日へ入れることは、今日の予定の枠を足すこと（`addSession`）になり、新しいデータが要らない。時刻は利用者が決める（初期値は、今を 15 分刻みに切り上げた時刻から 60 分。`planDefault`）。左の列へのドラッグ＆ドロップも、落とした位置から時刻を推し量って置かず、同じ入力欄を開く（左の列には時間の軸が無いため）。見送った案: ① 押すだけで、空いている時間に自動で入れる（意図しない時刻に入り、驚く）。② 時刻を決めない「今日やる」の印を持つ（個人ファイルに新しい項目が増え、枠から導く今日の ToDo と二重に管理することになる）。
- **週表示の今日の列には、背景色を付けない（日付の見出しの塗りつぶしと、列の上端の `--accent` の線（5px）と、現在時刻の線で示す）**: 背景色があると、予定の枠（`--accent-soft`）や会議の色と重なって見分けにくいため（利用者の判断）。見送った案: 予定の枠と違う色（薄い黄）の背景（利用者が、背景そのものをやめると決めた）。日表示にも、今日の背景色はない。
