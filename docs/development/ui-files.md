# 画面の動き: ファイル・設定・保存

ファイルを開く、設定タブ、祝日の取得、共有・個人ファイルの分割、保存と競合。[開発者向けの情報](../development.md)の一部。

## ファイルを開く（開始画面・バナー）

- 画面は、共有ファイル（`data.json`）と個人ファイル（`personal.json`）の 2 つを開く。2 つとも開くまで、ガント以降を描かない（開始画面）。起動時は `restore()` で、権限が許可済みの方だけ自動で開く。
- 開始画面は、開いていない方（`missing()`）ごとに、案内（「共有ファイルを選んでください」・「個人ファイルを選んでください」）と、選ぶボタン（`data-open="shared"`・`data-open="personal"`）を出す。押すと `choose(which)` で、2 つ揃ったときだけ `loaded` で画面を開く。揃わなければ開始画面のまま、足りない方の案内だけを出す。
- 「前回のファイル（…）を開く」（`data-reopen`、`reopen()`）は、開いていない方に記憶があるとき（`lastFile()` の名前）だけ出し、その名前を並べる。権限の確認だけで開く。
- 開始画面のボタンは、プロジェクトの絞り込み（ガントの `data-open`）と同じ属性名なので、`#view` のクリックでは、データが無い（`!S.data`）ときだけ、ファイルを選ぶボタンとして扱う。
- 札の詳細の「別の共有ファイルを選ぶ」・「別の個人ファイルを選ぶ」（`data-open`）は、選んだ方だけを差し替える（もう片方は開いたまま）。開けなかった理由は、開始画面では画面に出し、画面が開いているとき（`S.data` がある）は、通知（`toast`）で出す。
- 直接保存に対応しないブラウザ（`showOpenFilePicker` が無い）では、開始画面に、2 つのファイルを一度に選ぶ入力欄（`<input type="file" multiple>`）を出す。共有か個人かは、中身の形で見分ける（`dataFromTexts`: `projects` が配列なら共有、そうでなければ個人。共有 1・個人 1 でなければ、「1 つずつ選んでください」で開かない）。保存は、画面上部の「JSON を書き出す」が、`data.json`・`personal.json` の 2 つを 0.3 秒の間隔で続けてダウンロードする（`exportFiles`）。ブラウザが、続けて複数のダウンロードをする許可を尋ねることがある（未確認）。1 つのファイルを、データ全体として読む経路は持たない。
- 共有に無いタスクの作業枠（`data.orphanSessions`）: バナーは、注意の文のあとに、ボタン「該当の枠を削除」（`data-orphan-clear`）を出す（`common.js` の `bannerHtml`）。押すと `S.pendingOrphan`（メモリのみ）が立ち、「N 件の作業枠を削除します。タスクが戻っていないか、少し待ってから確認してください」と「削除する」・「やめる」に変わる。「削除する」は `apply((d) => removeOrphanSessions(d), …)` で、`orphanSessions` を空にするだけ（タスクと枠は変えない）。保存はふつうの編集と同じ道（`sync.persist` → `createPairStore`）で、変わるのは個人ファイルだけ。確認を挟むのは、共有ファイルの同期（SharePoint など）が遅れて、タスクが一時的に見えないだけのことがあるため。`orphanSessions` の枠は、カレンダー・優先度・稼働には描かない（`tasks[].sessions` だけを読む）。
  - 削除のボタンと確認は、検証の注意のバナー（`refreshBanner` が出す `validated` つき）にだけ付ける。保存の失敗・「読み直せません」・「直接保存できません」のバナーには付けない（付けると、再読込・書き出しのボタンを押す前に上書きしうるため）。`banner()` は直前の文と操作を覚え、削除のボタン・やめる・削除するは、それを描き直すだけで、検証の結果で上書きしない。`sync.js` が保存の失敗から戻ったときは、失敗の印を下ろしてから `banner("")` を呼び、画面は、空の文を「検証の結果を出し直す」と読む。
  - バナーの文は `refreshBanner`（`validate` の結果）で出し直す。ファイルを開いたとき（`loaded`）・読み直しの成功（`reloadFile`）・`sync.js` が他の更新を取り込んで `setData` するとき（保存の失敗中を除く）に出し直すので、タスクが戻って `orphanSessions` が空になれば、バナーとボタンは消える。確認の状態（`S.pendingOrphan`）も、そのとき下ろす。
  - 「削除する」は、保存が競合して最新のファイルに当て直されると、確認を出したあとに増えた共有に無い枠も、まとめて消す（当て直しは編集 `removeOrphanSessions` を最新のデータに掛け直すため。確認の件数と食い違いうる。許容した）。
- 読み直し（「更新」・バナーの再読込）は、`reloadFile` だけが `store.reload()` を呼ぶ。読み直せなくても、`sync.reset()` で保存していない編集を捨て、再読込・書き出しのボタンつきのバナー「読み直せません: …（画面の内容は、まだファイルと違う可能性があります）」を出す。残る穴: 読み直せなかったとき、画面のデータ（`S.data`）には、捨てると伝えた編集が残り、次の保存で、外から変わっていない方のファイルには、そのまま書かれうる（読めないのでデータを差し替えられない）。
- 動作確認（Playwright、Chromium、`file://`、`?today=2026-10-20&time=10:15`）: `showOpenFilePicker` とファイルのハンドルを偽物に差し替え（中身は `splitData(data/sample.json)`、IndexedDB の記憶はハンドルの名前に置き換えて保存）、(a) 共有 → 個人の順に選ぶと画面が開く、(b) 共有だけのときは個人の案内とボタンだけが出る、(c) 再読み込みで 2 つとも自動で開き、権限が未確定（`prompt`）のときは「前回のファイル（data.json・personal.json）を開く」が出て、押すと開く、(d) 個人の記憶を消すと、共有だけが開いて個人の案内になる、(e) タスク名の変更は data.json だけを書く（個人の設定の変更が personal.json だけを書くことは、いまある項目では未確認）、(f) 共有ファイルを壊して「更新」すると、「読み直せません」のバナーが出る。共有に無い枠を足した個人ファイルで、バナーに注意の文とボタンが出る・スケジュールにその枠は出ない・ボタン → 確認 → 「やめる」で戻る・「削除する」で個人ファイルからその枠だけが消える（共有は変わらない）・共有にタスクを足して「更新」するとバナーが消える。`showOpenFilePicker` を消した状態では、2 つのファイルを入力欄で選ぶと画面が開き、「JSON を書き出す」が `data.json`・`personal.json` の 2 つをダウンロードした（中身のキーは分割後の形）。
- 未確認: 実際のファイル選択と権限の確認の画面（Edge・Chrome）、1 回の押下で 2 つの権限の確認が続けて出せるか、定期の読み直し（`pollInbox`）経由でのバナーの消え方、ネットワークドライブ・SharePoint 経由のファイル、保存の失敗中の個人ファイル側の再現、`showOpenFilePicker` の無い実ブラウザ（Firefox・Safari）での 2 つのダウンロード。

## 設定タブ

- **節の構成と折りたたみ**: 節は 4 つ（基本の設定・休みと営業日・キーワード規則・WBS の取り込み記録）。「休みと営業日」の中に小見出しが 3 つ（日本の祝日・休み（手動）・営業日として扱う日）ある。7 つとも `<details>` で、見出しを押すと開閉する。
  - 開閉は `S.settingsClosed`（閉じている節の ID の配列。ID は `prefs.js` の `SETTINGS_FOLDS`）に持ち、`localStorage`（`project-lens.settingsClosed`）に保存する。保存が無い・壊れている・使えないときは、すべて開く。`data.json` には保存しない（ブラウザごとの好みのため）。
  - `app.js` が `toggle` イベントをキャプチャで受けて記録する（`toggle` はバブリングしない）。開閉では描き直さない。描き直したときは、`renderSettings` の `opts.closed` から開閉を復元する。
  - 閉じた節の中の入力と `validate` の注意も、HTML には描く（見えないだけ）。閉じた節の見出しには「注意 N 件」を出す（`fold` の第 6 引数。親の「休みと営業日」は 3 つの小見出しの合計、「キーワード規則」は `ruleError` の有無で 1 件）。画面上部のバナーにも、`validate` の注意は元から出る。
  - 動作確認: 描画と保存は `npm test`。実ブラウザ（Chromium、Playwright）で、クリックとキーボード（Enter）での開閉、保存、再描画後と再読み込み後の復元、注意の件数の表示を確認した。描画時に `open` の節で `toggle` が発火するが、記録は変わらない。スクリーンリーダーでの読み上げは未確認（Chromium のアクセシビリティツリーでは、見出しは heading として出る）。
- **基本の設定**: 営業日の数え方・待ち長期化の日数・見出しの呼び名を、その場で保存する（`updateSettings`）。勤務時間の行は無い（設計判断を参照）。
  - 保存に成功したら描き直さない（描き直すとフォーカスが消える）。
  - 不正な値は、先に検査して通知し、入力欄だけを保存された値（形が違えば既定値）に戻す（`restoreSettingInputs`。描き直すとフォーカスが消えるため）。
  - 形が違う値は `validate` が注意（warning）にし、設定タブは既定値を入力欄に出して横に注意を出す。
- **キーワード規則**: ↑↓で並べ替えられる（`moveProjectRule`）。上の規則が先に当たるので、並べ替えたら会議へ付け直す。
- **営業日の数え方**: 「基本の設定」の表の先頭の行。チェックボックス `data-set="countWeekendsAndHolidays"` が `settings.countWeekendsAndHolidays` を保存する（`updateSettings`。`false` ではキーを消す）。他の入力と違い、保存後に描き直す（「日本の祝日」「休み（手動）」の小見出しの説明を切り替えるため）。`true` 以外（`"true"` など）はオフとして描き、`validate` の注意をその行に出す。
  - オンのとき、`calendarOf` は `off` を手動の休みだけにして `countWeekends: true` を足し、`dueAfter` は土日を飛ばさない。`holidayRangeDays` は期間の全日を返す（除外は 0）。祝日の自動取得（`needsHolidayUpdate`、`propose` の取得と範囲の注意）は行わない。保存済みの `nationalHolidays` は消さないので、オフに戻すと再び使う。
  - ガントの土日の色分け（`metrics.js` の `timeTicks`）は、曜日の表示であり営業日の計算ではないので、オンでも変えない。
  - 実機（Playwright）での確認は未確認。
- **日本の祝日・休み・営業日**: 「休みと営業日」の節の中の 3 つの小見出し。`validate` は 3 つの形が違うとき注意（warning）にし、画面は壊れた値を空として描いて小見出しの下に注意を出す。
  - 「日本の祝日」: `settings.nationalHolidays`。読み取り専用。取得は `tools/holidays.js`（営業日を使う提案では `tools/inbox.js propose` も必要なら取得する。「日本の祝日の取得」を参照）。
  - 「休み（手動）」: `settings.holidays`（`{date, kind, note}`）。`addHoliday`・`addHolidayRange`・`removeHoliday`。終了日を入れると期間を 1 日ずつに展開し、土日と取得済みの日本の祝日を除く（土日祝を営業日に数える設定のときは、何も除かない）。`holidayRangeDays` が除外の数を返し、`app.js` が通知する。
  - 「営業日として扱う日」: `settings.workdays`。`addWorkday`・`removeWorkday`。

## 日本の祝日の取得

- `tools/holidays.js` の `update` が、内閣府の `syukujitsu.csv`（Shift_JIS）を取得して、前年以降だけを `nationalHolidays` に書く。失敗したら `data.json` を変えず終了コード 1。
- `status` は、取得日・件数・範囲・`ageDays` を出す。取得先は環境変数 `PROJECT_LENS_HOLIDAYS_URL` で変えられる。
- ブラウザからは CORS で取れないため、画面は取得しない。
- 更新の判定は `tools/holidays.js` の `needsHolidayUpdate(settings, neededUntil)`（未取得／取得から 30 日超／一覧の最終日が今日以前／`neededUntil` が一覧の最終日より後。今日取得したものは取り直さない。`settings.countWeekendsAndHolidays` が `true` のときは、常に取り直さない）。入口は 2 つ: `tools/holidays.js ensure`（`/project-lens:watch` を始めるとき。当てはまるときだけ取得し、失敗したら終了コード 1 で `data.json` を変えない）と、`tools/inbox.js propose`（`businessDays` を使う提案のとき、当てはまれば同じ取得を 1 回行って提案と一緒に保存する。取得できなかった・範囲を超えたままのときは、提案の `warnings` に書く。エージェントは祝日を確かめない）。手動で取るときは `tools/holidays.js update`（コマンド `/project-lens:holidays` はない）。
- 解析は `core/holidays.js` の純関数（`parseHolidayCsv`・`pickRecent`・`decodeHolidayCsv`）。

## 共有ファイルと個人ファイルの分割

データは、メモリ上では 1 つのまとまり（`S.data`）で、ファイルでは 2 つに分かれる。変換は `core/split.js` の純関数（`splitData`・`mergeData`）だけが行い、画面の各部・CLI の各コマンドは、結合した 1 つのデータのまま扱う。

| ファイル | 置くもの |
|---|---|
| 共有（`data.json`） | `projects`・`tasks`（作業枠 `sessions` を除く）・`changeLog`・`version`・未知のトップレベルのキー、設定のうち個人以外すべて（既知のものは `countWeekendsAndHolidays`・`nationalHolidays`・`waitingLongDays`・`projectRules`・`labels`・`wbsMappings`・`wbsImports`。未知のキーも共有） |
| 個人（`personal.json`） | `sessions`（`taskId` を持つ平らな配列）・`events`・`inbox`（あるときだけ）・`reviews`（空でないときだけ）・`version`、設定のうち `holidays`・`workdays`・`selfEmails`・`selfNames`（`PERSONAL_SETTINGS`） |

- 個人ファイルの未知のトップレベルのキーは、結合で落ち、次に個人ファイルを書くときに消える（共有ファイルの未知のキーは残る）。結合したデータからは、どちらのファイルのキーだったか分からないため（残すには、個人のキーの一覧か印が要る。いまは個人ファイルに未知のキーを書く道具がないので、見送った）。
- 同梱のサンプルは `data/sample.json` 1 つで、分割前の結合した形（メモリ上の形）。`data/personal.json` のサンプルは無い。`init --sample` は、これを `splitData` して 2 つのファイルを書く。エージェントの指示がスキーマとして `sample.json` を指すのは、この結合した形のこと。サンプルとテストの ID は、採番する形にそろえる（プロジェクト `AA`〜`AC`、タスク `AA-0001`、プロジェクトなし `ZZ-0001`）。ID の形は検証しないが、例が実際の形を示すようにするため。ID の形を検証しないので、手で書いた別の形の ID（`A1`・`A` など）も受ける。採番（`nextProjectId`・`nextTaskId`）がそうした ID を無視することは、`edit.test.js` で確かめている。テストに出てくるほかの `A`・`A1` は ID ではない（プロジェクト名、大項目の名前、WBS の件名・前のタスクのキー、Excel の値・セル番地）。

- 結合（`mergeData`）は、個人の枠を `taskId` でタスクの `sessions` へ戻す。個人ファイルに、廃止した個人の ToDo（`todos`）が残っていても、エラーにせず捨てる（結合したデータに `todos` を出さない）。`taskId` がその ToDo の `id` の枠も捨て、`orphanSessions` にも入れない（共有のタスクの ID と同じなら、タスクの枠として戻す）。`splitData` は、入力に `todos` があっても、どちらのファイルにも書かないので、読んで保存し直すと消える。`checkPersonalShape` は `todos` を検査しない。共有に無い `taskId` の枠は、`orphanSessions` に入れる（消さない。バナーの案内は「画面の動き > ファイルを開く」）。`splitData` は `orphanSessions` を個人の `sessions` へ戻すので、保存しても失われない。入力は変えない。
- 形の検査は `checkSharedShape`（`projects`・`tasks`・`changeLog` が配列）と `checkPersonalShape`（`sessions`・`events` が配列）。画面に渡す前に、2 つとも通す。`validate` は、共有に無いタスクの枠を注意（warning）にする。
- 旧形式（作業枠がタスクの中にある 1 ファイルの `data.json`）の移行・読み替えは持たない。旧形式のファイルは、手で直す。`checkSharedShape` は、タスクのどれかに `sessions` のキーがある、またはトップレベルに `events` があるとき、「作業枠・予定を含む 1 ファイルの旧形式の data.json です。personal.json へ手で分けてください」で例外にする（`isOldShared`）。読むと、個人ファイルが無い・空のとき、枠・予定が空のデータになり、次の保存（見張りの印の保存は `.bak` を作らない）で共有ファイルから消えるため。`splitData` は共有ファイルにどちらも書かないので、正しいファイルでは起きない。CLI の `readData`（`validate.js` を含む）・画面の `createPairStore`・`dataFromTexts` が、この検査で止める。`init` も、既存の `data.json` が旧形式なら、空の個人ファイルを隣に足さず、何も変えずに止める（読めない・形の違うファイルは、これまでどおり変えない）。
- 設計判断（なぜ分けたか）: 複数人でスケジュールを管理するとき、タスクは全員で共有し、作業枠・会議・休み・自分の特定・依頼は各自のものだから。
  - 見送った案（作業枠をタスクの中に残す）: 全員の作業枠が共有ファイルに入り、1 人の枠の編集のたびに共有ファイルが更新され、競合の当て直しが増える。他の人の予定も共有ファイルから見える（この理由は、分割の目的からの推測。試していない）。
  - 見送った案（https の URL での直接の読み書き。Microsoft Graph など）: 利用者の判断。ネットワークドライブ・同期フォルダ経由の共有ファイルで足りるため。
  - 見送った案（他の人の稼働・個人ファイルの表示、タスクの担当者の項目）: 利用者の判断。必要になってから足す。読むのは自分の個人ファイルだけ。
  - 見送った案（2 つのファイルをまとめて書く・競合を確かめる仕組み）: 利用者の判断。ファイルごとに独立して保存し、片方だけ書けた場合は、下の「保存と競合」の規則で扱う。
  - 見送った案（共有ファイルだけで開く動き）: 利用者の判断。個人ファイルが無いときは、画面を開かない。

## 保存と競合

保存と競合の検知・当て直し・自動の読み直しは、ファイルごとに独立している（ファイルごとに読み込み時点の印を持つ）。ロックは作らない。

#### CLI（`tools/cli.js`）

- CLI の保存（`saveData`）は、`readJson` で読んだ時点のファイルの印（更新日時とサイズ）を覚え、書く直前に比べる。違えば「他で更新されました」で止まる（もう一度読み直して実行する）。見張りの印を書く `wait` は、止まったら次の回に書く。`readJson` は、先頭の BOM（メモ帳などが付ける）を除く（画面は `file.text()` が除くので、そろえる）。置き換えが 3 回失敗したときは、上書きせず例外にする。
- 2 ファイルの読み書きは `readData`・`saveData`。共有ファイル（`data.json`）と個人ファイル（既定は同じフォルダの `personal.json`、`--mine <ファイル>` で別の場所。相対パスはいまのフォルダから）を、結合して扱う。`inbox.js`・`intake.js`・`holidays.js`・`validate.js` が使い、`init.js` は 2 ファイルを直接書く。`doctor.js` は保存先のフォルダだけを見るので変えない。
  - `--mine` に値が無い（末尾・空）ときは、既定の場所へ黙って戻さず、`--mine にファイルを指定してください` で終了コード 2（`takeMine` が例外、各ツールの入口 `takeMineOrExit` が終了コードにする）。
  - 既定の個人ファイルが無い（`ENOENT`）ときだけ、空の個人として読む。`--mine` で明示したファイルが無いときは、指定の誤りなので、空として読まず「個人ファイル … がありません。--mine の指定を確かめてください」で例外にする（`saveData` も、共有を書く前に同じ例外）。共有ファイルが無い・形が違うときも例外。
  - 読んだとき個人ファイルが無かった場合は、その印を覚え、保存の確認と書く直前に、他が作っていないかを見る。作られていたら、空の個人で上書きせず「他で更新されました」で止める。読んだあとに消されたファイルも、同じ文言で止める。
  - `saveData` は、結合したデータを `validate` に 1 回だけ通し、エラーなら何も書かない。通ったら分けて、中身が変わった方だけ書く（共有だけの変更で、個人ファイルの更新日時を動かさない）。
  - 書く前に、両方のファイルの競合を確かめる（片方を書いてから、もう片方の競合に気づく形にしないため）。書く順は、共有 → 個人。2 つ目の置き換えが失敗したときは、1 つ目を巻き戻さず、例外の文言に、書けたファイルと書けなかったファイルを書く（巻き戻しも別の書き込みで、失敗しうるため見送った）。たとえば `inbox approve` で、共有（タスクの変更）は書けて個人（依頼の状態）が書けないと、依頼は `proposed` のまま残る。もう一度 `approve` すると、提案の時点からタスクが変わっているので、古い提案（`stale`）として止まり、依頼は失敗の状態になりうる（未確認）。
  - `init.js` は、cwd 自身に `.project-lens/data.json` が無く、親のフォルダのどこかにあるときは、何も作らず止める（`parentWithData`）。子フォルダで Claude Code を開いて、案内どおりに `init` を実行すると、親とは別の 2 つ目のデータができ、画面で選ぶファイルと見張りが見るファイルが食い違うため。自動で親へ移って実行する案は見送った（別プロジェクトを子フォルダで新しく始める意図を壊すため。その場合は、親のデータを避けて、親の外のフォルダで始める）。
  - `init.js` は、`saveData` を通さない（`--mine` で指す個人ファイルは、作る前で、まだ無いから）。既存のファイルは変えない。共有だけがあるときは、空の個人ファイルを作る（サンプルの個人データは、既存の共有と合わないので足さない）。共有を新しく作る `--sample` の隣に個人ファイルが既にあるときは、個人ファイルは変えず、「変えていません。サンプルの作業枠・予定は入っていません」と 1 行出す。`--sample` は、分割前の形の `data/sample.json` を `splitData` して書く。`.gitignore` に足すのは `.project-lens/` だけなので、`--mine` で `.project-lens/` の外を指した個人ファイルは、除外されない（利用者が自分で除外する）。
- 控え（`.bak`）: 検証と競合の確認に通ったあとに、直前の版を `<ファイル>.bak.tmp` へコピーしておき、置き換えに成功したあとで `<ファイル>.bak` にする（置き換えに失敗したときは、`.bak.tmp` を消し、1 つ前の `.bak` を残す。先に `.bak` を上書きすると、置き換えの失敗で 1 つ前の版を失うため）。書いたファイルごとに 1 世代（`data.json.bak`・`personal.json.bak`）。誤承認・誤った WBS の取り込み・予定表の誤削除を、戻せるようにするため。`.project-lens/` は git の対象外（`init` が `.gitignore` に追記する）で、`.bak` も同じフォルダなので同じ除外に入る。
  - 1 世代だけで、上書きする。元のファイルが無い（初回）ときは作らない。`.bak` が書けなくても、標準エラーに 1 行（`<パス>.bak を更新できませんでした: <理由>`）を出して、本体の保存は続ける（控えは補助で、止めると本体より副の機能が優先になるため。出さないと、古い `.bak` が新しい控えに見える）。検証に通らず例外のときは作らない。見張りの印だけの保存（`tools/inbox.js` の `wait`）は `{ backup: false }`（30 秒ごとに `.bak` を上書きすると、意味のある直前の版が消えるため）。
  - 効く範囲: `.bak` を作るのは CLI の保存だけ。画面の承認・編集は作らない。見張り中は、依頼のやりとり（claim・ask・propose など）や 30 分ごとの `calendar-auto` の保存で、すぐ上書きされるので、戻せるのは直後だけ。戻す前に `.bak` の更新日時を確かめる。画面での編集は `.bak` に入らないので、戻すとその分も失う（利用ガイドに同じ注意を書いている）。
  - 見送った案: 世代管理（日時付きの複数の控え。戻す場面は「直前の誤操作」で、1 世代で足り、ファイルの掃除の規則が要るため）。画面（`store.js`）側の `.bak`（画面は `showOpenFilePicker` で得たファイルのハンドルに `createWritable` で書く方式で、フォルダのハンドルを持たない。同じフォルダへ別ファイルを書くには別の権限が要ると考えられるが、実ブラウザでは未確認。画面での編集の誤りは、CLI 側の `.bak` ではなく、画面の「JSON を書き出す」で退避する）。

#### 画面（`ui/store.js` の `createStore`・`createPairStore`、`ui/sync.js`）

- `createPairStore` は、共有（IndexedDB のキー `dataFileHandle`、`checkSharedShape`）と個人（キー `personalFileHandle`、`checkPersonalShape`）の 2 つの `createStore` を持ち、結合した 1 つのデータ（`mergeData` の形）で受け渡す。画面は `createPairStore()` を使う。
- 開く: `choose(which)`（`"shared"` か `"personal"`）・`restore`・`reopen` は、2 つとも開いたときだけ結合したデータを返し、そうでなければ `null`。まだ開いていない方は `missing()`、記憶した名前は `lastFile()`（`{ shared, personal }`）。`hasFile` は 2 つとも開いているときだけ真。`reopen` は、開いていない方のうち記憶のある方だけ、権限の確認を続けて出す（記憶の無い方は開かず、`missing()` に残す。開こうとすると「書き込みが許可されませんでした」という誤った文言になるため）。
- 開く・読み直すときは、`createStore` が、画面に渡す前にデータの形を検査する（共有は `checkSharedShape`、個人は `checkPersonalShape`）。別のファイルを開く・前回のファイルを開く・自動オープンは、読めて形が合ったときだけ、保存先と記憶を切り替える（`switchTo`）。先に切り替えると、形が違って開けなかったファイルへ、画面に残った前のデータを保存し、そのファイルを丸ごと上書きするため。形が違うときの読み直し（「更新」・自動）は、画面のデータを差し替えずに、例外（自動のときは次の回に再試行）にする。形は合うが `validate` に通らないデータは、バナーを出して開く。JSON として読めないファイルは「JSON として読めません（<ファイル名>）」で開かない（`createStore` と `dataFromTexts`。`dataFromTexts` は、画面が渡すファイル名を使う）。
- `reload` は、2 つのファイルの最新を `mergeData` した形を返す。`changed()` は、読み込み（または直近の保存）のあとに、どちらかのファイルの更新日時が変わったかを返す（中身は読まない）。`ui/sync.js` の `pollInbox` は、`changed()` が `false` なら読み直さない。自分の保存では読み込み時点が進むので、`true` にならない。
- 保存（`save`・`saveMerged`）は、`splitData` で分けた 2 つのうち、直前に読んだ（保存した）内容から変わった方だけを、共有 → 個人の順に、それぞれの `createStore` で書く。比べるのは、直前の内容を `splitData(mergeData(…))` した形（ファイルのキーの順の違いで、変わっていない方を書かないように）。書く前に、ファイルごとに、更新日時を比べ、他（Claude Code など）が更新していたら上書きせず conflict を返す。
- 当て直し（`saveMerged` の競合）は、「そのファイルの最新」と「もう片方の、編集を当てる前の内容」を `mergeData` し、`edit` を当て、`splitData` で取り出したそのファイルの分を書く。当て直したときは、結合した最新を `data` で返す（当て直していなければ、渡したデータそのもの）。画面のデータは `mergeData` の形になる。当て直せなかったとき（同じ依頼がすでに処理されていた、など）だけ、保存時に「他で更新されました。再読込してください」と出て、上書きしない。読み直すと、画面の保存できていない変更は消える。
- 当て直しの保存が失敗したとき（書き込みの権限・I/O のエラー）は、読み込み時点（`loadedAt`）を元に戻す。進めたままだと、次の保存が競合を検出せず、画面の古いデータで他の更新を上書きする。
- 片方だけ成功したとき: 結果は `{ ok: false, reason, message: "<data.json か personal.json>: …", data }`。書けた方は、その内容と `loadedAt` を進め（次の保存で競合にしない）、失敗した方は直前の内容のままなので、次の保存で書き直す。巻き戻しはしない（CLI と同じ理由）。ファイル名は、実際のファイル名でなく、`data.json`・`personal.json` で出す（`--mine` で別名の個人ファイルを選んでも同じ）。
- 片方だけ成功したとき、書けた方を当て直さずに書けていたら、そのファイルの「編集を当てる前の内容」を覚える（`prior`）。`sync.js` は、失敗した保存の編集を持ったまま次の保存で当て直すので、失敗した方の当て直しの土台は、書けた内容ではなく、これにする（書けた内容を土台にすると、同じ編集を 2 回当てる。ID を編集の中で決めるタスクの追加なら、共有のタスクと個人の枠の ID がずれる）。書けた方自身も、次の保存では `saveMerged` でなく `save` で書く（その間に外から変わっていたら conflict）。`edit` の無い `save` は、そのまま書ける。すべて成功する・読み直す・開き直すと消える。
- 画面のデータが、片方のファイルより古くなったとき（書けた方を当て直していて、もう片方が失敗した）は、そのファイルの、編集を当てる前の内容を覚える（`behind`）。次の保存では、画面のデータではなく、その土台に `edit` を当て直したものを、`saveMerged` でなく `save` で書く（画面の古いデータで、他の更新を上書きしないため）。その間にそのファイルが外からさらに変わっていたら、2 回目の当て直しはせず conflict（すでに書いた編集を 2 回当てないため。利用者が再読込する）。`edit` の無い `save` も conflict。読み直し・開き直しが両方とも通ると消える。
- `reload` は、2 つとも読めて形が合ってから、両方の読み込み時点を進める（子の `read` で読み、`commit` で進める）。片方でも読めない・形が違うときは、何も変えずに例外（何も読み直さない）。片方だけ進めると、画面の古いデータが、その方の他の更新を競合なしで上書きするため。何も変えなければ、次の保存は競合になり、ふだんの当て直しで追いつく（読み直した内容を土台にする案は、`sync.js` がまだ持つ、書けた編集を 2 回当てるので見送った）。
- 保存と読み直しの順序づけは `ui/sync.js`（`createSync`）。画面の編集を 1 本の列に並べて保存し、競合したら最新のファイルに同じ編集を当て直す。Claude Code の更新の読み直し（`pollInbox`）も同じ列に並べる。画面は、ファイルを自動で読み直す（保存できる環境のとき）。帯が開いている間や依頼の処理中は 4 秒、そうでなければ 16 秒ごと。
- 打ちかけの入力の間は、読み直しの描き直しを待たせる: `createSync` の `isEditing`（`app.js` の `isEditing`）は、`#view` の中のフォーカスのある入力欄（`input` の文字・日付・時刻などと `textarea`。チェックボックス・選択欄は除く）の `value` が `defaultValue`（描いたときの値）と違うときに真。真の間、`pollInbox` は `setData` でデータだけ取り込み、`render` を `sync.flush()` まで待たせる。`app.js` は、`#view` の `change`（その欄の `onChange` のあと）と `focusout`（フォーカスが移り終わったあと）で `flush` を呼ぶ。`flush` は、まだ打ちかけなら何もしない。ほかの理由の `render` は、待たせた描き直しを捨てる（`sync.rendered()`）。ファイルを開き直す（`sync.reset()`）ときも捨てる。打ちかけでなければ、すぐ描き直す。受信箱だけの変化（`renderBar`）は `#view` を描き直さないので、待たせない。
  - 確定で下書き・データに写さない欄（チェックリストの追加欄 `data-ckadd`、待ち先の入力 `data-waitparty` など）は、フォーカスが離れたあとの描き直しで、打った文字が消える（直していない）。保存の当て直し（`persist`）の描き直しは、待たせない。会議の入力欄など、コードが値を入れ直した欄（`endInput.value = end` など）は、`value` が `defaultValue` と違ったままになるので、フォーカスが離れるまで描き直しを待たせる。
  - マウスのボタンを押している間（`pointerdown` から `pointerup`・`pointercancel` まで。3 秒で打ち切る）は、`flush` をしない。押した瞬間の `change`・`focusout` で描き直すと、押したボタンが作り直され、離したときのクリックが届かない（1 回目のクリックが効かない）ため。離したあと（`click` の処理のあと）に `flush` する。キーボードでの移動（Tab）は、すぐ `flush` する。
  - 動作確認（Chromium・Playwright、`?today=2026-10-20&time=10:15`、`showOpenFilePicker` を偽のファイルに差し替えて `splitData(sample.json)` を読み込んだ）: 突発タスクの件名を打ちかけのまま、外から共有ファイルのタスク名を変えて 17.5 秒待つと、件名は残り、画面はまだ古い。フォーカスを外す・Tab で次の欄へ移ると、新しいタスク名が出て、件名も残り、フォーカスは次の欄にある。打ちかけでないときは、読み直しですぐ新しいタスク名が出る。未確認: 実際の日本語入力（IME）の変換中、ほかの入力欄（編集の窓・スケジュールの編集欄・会議・リスト・チェックリスト）。
- 直接保存に対応しないブラウザでは、「JSON を書き出す」が 2 つのファイルをダウンロードする。読み込みは、2 つのファイルを一度に選ぶ（「画面の動き > ファイルを開く」）。

#### 見送ったこと・未確認

- 見送ったこと（既知の穴）: 保存の確認と書き込みの間の競合。CLI も画面（`store.js` の `save`）も、「更新日時を見る → 書く」の 2 段階で、プロセスをまたぐロックはない。確認と書き込みの間（数ミリ秒）に相手が書くと、その編集は検出されず消える。起きうる組み合わせは、見張り（`wait`）の見ている印（30 秒ごとに個人ファイルを書き直す。共有ファイルは書かない）と、画面での個人ファイルの編集が、同じ数ミリ秒に重なるとき。消えるのは直前の 1 回の編集で、画面なら再読み込みの後に気づく。ロックファイルは、小さな規模には過剰なので入れない。1 つの共有ファイルを複数人が使うと、共有ファイルでは、人どうしの編集が同じ数ミリ秒に重なる組み合わせも加わる。確認していないこと: 実際に編集が消えるかを、2 つのプロセスで同時に書いて試していない（未確認）。
- 実ブラウザで未確認: 2 つのファイルの権限の確認、自動の読み直し（`pollInbox`）と組み合わせた動き、SharePoint・ネットワークドライブ上のファイルでの更新日時の扱いと自動の読み直しの遅さ。
- 枠の長さを変える操作（`resizeSession`）も、移動・追加と同じく、会議と重なるときは `warning` を返す。画面は、操作の結果の文に添える。
- 前回のファイルの記憶は、Edge で `file://` から開いて効くことを確認した。権限の確認の文言は Edge のバージョンで違う想定で、実際の文言と「何も押さずに開く」動きは未確認。
