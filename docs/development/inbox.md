# HTML からの依頼（inbox）

HTML の「Claude Code に依頼する」から届く依頼の処理。[開発者向けの情報](../development.md)の一部。

## 動き

- 処理待ち（`pending`）・処理中（`working`）の依頼にも、画面に「却下する」を出す。見張りが止まる、受け取った後にセッションが落ちるなどで、`wait` が知らせない依頼（`working`）は、誰も処理しない。画面から取り下げられるようにした。見送った案: `wait` が受け取って長く経った `working` を再通知する（`submit --working` の依頼と区別する材料が要る）。

- 画面の下端の帯「Claude Code に依頼する」から、日程の見直し（`moveDue`）・タスクの登録（`addTask`）を依頼する。依頼は個人ファイル（`personal.json`）の `inbox` に書かれ、見張っている Claude Code が提案（変更案）を作る（承認すると、タスクの日程は共有ファイル（`data.json`）に書かれる）。承認するまで、タスクの日程・前のタスク・一覧は変わらない。
- 依頼で受ける操作は `addTask` と `moveDue` の 2 種類だけ（`core/schema.js` の `PROPOSE_OPS`）。状態・重要の変更、削除、プロジェクトの追加と変更、マイルストーン、チェックリストの項目の変更、前のタスクの付け外しは、画面で行う。`inbox` エージェントは、そのような依頼に、`ask` で「この依頼は画面で行ってください」と返し、提案を作らない。
- できないこと: 会議の追加・削除。Excel の WBS・予定表・会議の規則の取り込みは `/project-lens:intake`。
- プロジェクトなしのタスクは、依頼の `addTask`（プロジェクトの指定が必須）・`moveDue`・WBS の取り込みの対象外。`moveDue` の影響の計算に、プロジェクトなしのタスクがあっても落ちず、前のタスクのないプロジェクトなしのタスクは、依頼の対象を絞る処理に含まれず、動かさない（直接 `moveDue` で指したときは、動く。単体テスト `tests/inboxops.test.js` で、対象の行に含まれず、期限が変わらず、検証の error が 0 件なことを確かめた。直接指したときの動きは、`planOps` で ZZ-0001 が +3 日になることだけ確かめた）。画面は、プロジェクトなしのタスクに前のタスクを付けさせない（`predecessorCandidates` が空を返す）ので、通常は連鎖で動かされない。ただし、影響の計算（`computeImpact`・`planOps`）はプロジェクトを見ないので、`data.json` を手で直して、プロジェクトなしのタスクに前のタスクを付けると、その前のタスクの遅れで連鎖して動く（サンプルの写しに、AA-0003 を前のタスクにするプロジェクトなしのタスクを足し、`planOps` で AA-0003 を +30 日にすると、そのタスクも同じ日に動き、`validate` の error は 0 件なことを確かめた）。実ブラウザ・実際の依頼の処理は未確認。
- 履歴は最新の 20 件まで（処理中のものは消えない）。1 件の文章は 4000 文字まで（やりとりの件数の上限は無い。「設計判断」（`design-decisions.md`）を参照）。
- 変更履歴には、期限を動かす操作ごとに 1 件（日数・理由つき）と、登録があるときの 1 件（`source` が `inbox`。画面の「日程変更の履歴」には出ない）が残る。登録の 1 件の `reason` は「受信箱: 登録 N 件・期限の変更 N 件」の形（要約も同じ形）。

## 反映の規則

- 操作は、`addTask`→`moveDue` の順に当てる（それぞれ書かれた順）。`addTask` の前のタスクは、全部足してから結ぶ。前のタスクを足したとき、次のタスクの期限が前のタスクより前なら、前のタスクの期限と同じ日まで動かす。
- `moveDue` で動かしたタスクの新しい期限（連鎖と引き上げのあとの値）には、次の警告を出す（提案は止めない）。休みの日（`offDayChecker`。土日祝を営業日に数える設定なら、手動の休みだけ）、今日より前、前のタスク（動かしていないもの・完了していないもの）の期限より前。動かした前のタスクより前になるときは、警告ではなく、前のタスクの期限まで引き上げる（上の「前のタスクを足したとき」と同じ規則）。次のタスクなど、連鎖で動いたほかのタスクの期限には、この警告を出さない。
- `addTask` には、文字列の配列 `checklist`（空文字は除く）を付けられ、反映するときに `c1` から採番する。`predecessors` と `moveDue` の `taskId` には、同じ依頼の `addTask` の `ref` を書ける。
- 承認時の `stale` の判定は 1 つ: いまのデータで操作をもう一度計算し（`simulate`）、変更案の表の同一性（`sectionsKey`。期限の行は ID・旧い期限・新しい期限、登録の行は `ref`・件名・プロジェクト・大項目・中項目・期限・前のタスク・項目の文言。開始日の既定と理由の文は含めない）が提案と違う、または計算できない（タスクやプロジェクトが消えた、完了した、など）ときは `stale`。触るタスクの値（`base`）との二重の比較はしない（表の比較で足りる）。保存済みの提案に `base` が残っていても、読まない。
- 保存済みの提案の `ops` に、`PROPOSE_OPS` 以外の操作（`OP_KINDS` のうち、画面で行う操作の名前）が残っていたら、承認は `stale` と同じ扱いで失敗にする（メッセージは「この操作は依頼では受けられません: <op>（画面で行ってください）」）。`propose` も同じ検査で拒否する。保存済みのデータの検証（`validate`）は、`OP_KINDS`（17 種類）を受けるので、古い依頼が残っていても保存できる。
- `--cause` は提案全体で 1 つ。原因が複数あるときは「その他」。
- 開始日のあるタスクに前のタスクを足しても、開始日は変えない（警告も出さない）。
- 提案のあとにデータが変わったときは、反映せず、依頼が「失敗」になる。「もう一度提案してもらう」で作り直す。先に Claude Code の画面で承認・却下した依頼を、HTML でもう一度承認しても、何も変わらない（二重には反映されない）。
- 期限を動かす `moveDue` と、`businessDays` 指定の `addTask` は、同じ依頼にできない。`planOps` が例外を投げる（前のタスクの期限が動くと、営業日が吸収されるため）。`agents/inbox.md` は、期限の移動だけを提案し、登録は承認後にもう一度依頼してもらう。`moveDue` と `due`（日付）指定の `addTask` は一緒にできる。

## 登録（`addTask`）の期限

- `due`（日付）か `businessDays`（営業日の整数）のどちらか一方。`businessDays` は 3650 日（約 10 年）まで（`dueAfter` が 1 日ずつ数えるので、打ち間違いで止まらないようにする）。
- `businessDays` は、完了していない前のタスクの期限の最大値（無ければ今日）から数えて、土日と休みを除いた日数後の日付になる。計算は `core/dates.js` の `dueAfter(base, businessDays, cal)`。
  - `cal` は `core/holidays.js` の `calendarOf(settings)`（`{off, on}`）。
  - `on`（`workdays`）の日は営業日、`off`（`holidays` と `nationalHolidays`）と土日は飛ばす。`on` が最優先。
  - `settings.countWeekendsAndHolidays` が `true` のときは、`calendarOf` が `off` を `holidays` だけにし、`countWeekends: true` を足す。`dueAfter` は `countWeekends` が `true` なら土日を飛ばさない。
- 営業日の計算は受信箱の登録だけで、期限の移動（`moveDue`）とドラッグの期限変更は暦日のまま。
- `propose` が `businessDays` を `due` に置き換えて提案の `ops` に保存するので、承認が翌日以降でも `stale` にならない（提案の表の `add` 行には `businessDays` が残る）。
- HTML の提案カードの登録の表には、行番号（`data-row`）と営業日の列が出る。「修正を依頼する」は暖色（`btn warm`）。

## 見張りと競合

- `tools/inbox.js submit ... --working` は、依頼を `working`（処理中）で作る。`wait` は `pending` だけを知らせるので、`/project-lens:watch` が動いていても `inbox` エージェントに横取りされない。
- `/project-lens:watch` は、Claude Code の Monitor で `node tools/inbox.js wait` を動かす。30 分ごとに終わるので、そのたびに再起動する。見張りが止まると、90 秒ほどで、帯が「見ていません」になる。見ている印（`inbox.watching.at`）が未来の時刻のときは、時計のずれとして 5 分先までだけ許す（それより先の印で、いつまでも「見ています」にならないように）。
  - 止めるときは、この会話で Monitor を起動したときに返ったタスク ID（張り直しと、見張りを何度か始めたときの分を含む、すべて）を `TaskStop` に渡し、以後は届いた依頼を処理しない。ID は、見張りの開始と張り直しの報告に出す（会話が圧縮されても、記録に残りやすくするため）。ID が分からないときは、止めたと記録し、終わりの通知が来ても張り直さず、届いた依頼も処理しない（見ている印は書かれ続けるので、HTML の帯は最長 30 分「見ています」のまま）。スキルの手順としての停止は、未確認（ID を渡して Monitor が止まることだけを確かめた）。
  - 作業中の Claude Code が、依頼のイベントを受け取って動くことは確認済み。
  - Claude Code が入力待ちの間に自動で起きることは、未確認。確認できないときは、作業中の Claude Code に「届いている依頼を処理して」と頼む（手動の入口のコマンドはない）。
- `wait` は、始めるときに共有ファイル（`data.json`）と個人ファイル（`personal.json`）を 1 回読み、読めない（パスの打ち間違い・壊れた JSON）なら、理由を標準エラーに出して終了コード 1 で終わる。`--timeout` が 0 以上の数、`--interval` が 0 より大きい数でなければ、終了コード 2。始めたあとに読めなくなった回は、確認を飛ばすが、`--timeout` の判定は行う（読めないだけで、終わらなくならないように）。
- `wait` が出すイベント（標準出力）は `request` と `end` だけ。見ている印（個人ファイルの `inbox.watching`）を書けないとき（共有・個人を合わせた検証に通らない、など）は、標準エラーに `見張りの印を書けませんでした: <理由>` を 1 行出し（同じ理由は続けて出さない。書けた回で、いったんリセットする）、次の回にもう一度書く。見張りと依頼の検出は止めない。未確認: Monitor が標準エラーを会話へ出すか（出なければ、利用者は、見張りの出力を見る場合にだけ気づく）。HTML で承認・却下されたことは、知らせない（利用者は HTML で見ている）。見送った理由: 知らせても利用者の操作が要らず、帯の「見ていません」と、画面を開いたときに出るバナー（`validate` の注意）が原因を示す。
- 保存の競合: Claude Code が、個人ファイルの受信箱や見ている印（30 秒ごとに更新）を書くので、画面での編集と、ファイルの更新が重なることがある。そのときは、画面が最新のファイルを読み直して、同じ編集を当ててから、もう一度保存する（編集は消えない）。
