# 日々の業務支援の強化（設計）

対象: ①画面での期限変更を履歴に残す ②`Waiting` に回答予定日を持たせる ③定例タスク（完了で次回を作る）。

## 目的

- 日々の運用で、日程が動いた事実が履歴から漏れない。
- `Waiting` のタスクを、待ち先の回答予定に沿って催促できる。
- 毎週・毎月の固定作業を、毎回登録し直さずに回せる。

## 目標・非目標

- 目標: 上の 3 つ。データの形は任意項目の追加だけで、`version: 1` のまま。既存の `data.json` はそのまま読める。
- 非目標: 後続への影響の表示、通知・要約、会議に連動した準備・事後タスクの自動生成、ひな形の管理画面、依頼の帯（inbox）と WBS での繰り返しの指定。
- 避けたいこと: 画面の操作が 1 手増えること。履歴が操作のたびに増えること。

## 案の比較（③定例）

| 案 | 内容 | 結論 |
|---|---|---|
| A. 完了で次回を作る | タスクに繰り返しを付け、Done にしたとき次の 1 件を作る | **採用**。変更が小さく、既存の完了の流れに載る |
| B. ひな形から自動生成 | ひな形を持ち、画面を開いたとき先の分を足す | 見送り。管理画面と重複防止が要る |
| C. B ＋会議連動 | 予定表の会議から準備・事後を作る | 見送り。A を使ってから判断する |

①は「黙って記録」（原因は後から選ぶ）、②は「回答予定日を任意で持つ」を、利用者が選んだ。

## ① 画面での期限変更の記録

- 画面から `due` が変わったとき、`changeLog` に 1 件足す: `{ at: 今日, taskIds: [id], reason: "画面で期限を変更", cause: null, deltaDays: 新期限 − 旧期限, source: "screen" }`。
- 対象の操作: リストの期限欄、ガントのバーのドラッグ（右端と中ほど）、編集の窓。開始日だけの変更は記録しない。
- 同じ日に同じタスクの `screen` の記録があれば、`deltaDays` を足して 1 件にまとめる。合計が 0 になったら、その記録を消す（ドラッグの試行錯誤で履歴を埋めない）。
- 履歴の行に原因の選択欄（ベンダー／社内／自分／その他）を出し、選ぶと `cause` を保存する。`source` が `screen` の行だけ。
- `schema.js` の `source` の許可に `screen` を足す。表示の絞り込み（`project.js`）は、`deltaDays !== 0` の行を出す現在の規則のまま。
- 「画面で期限を直接変えたときは記録されません」の注記を直す。

## ② `Waiting` の回答予定日

- `waitingOn` に任意の `expected`（`YYYY-MM-DD`）を足す。形が違えば `validate` が error。
- リストの待ち先の列に、日付欄を足す（編集の窓には待ち先の入力がないので足さない）。`Waiting` でないときは無効。
- 「今日の優先」: `Waiting` で `expected` が今日より前なら、+40 を足す。理由に「回答予定日を過ぎています（N日）」を出し、行の文言は「催促」にする。`expected` が空なら、今までどおり（期限超過のときだけ「催促」）。
- 優先順位の表（設計書の算出規則）に 1 行足す。

## ③ 定例タスク（完了で次回を作る）

- タスクに任意の `repeat`: `{ unit: "week" }` または `{ unit: "month", day: 1〜31 }`。`month` の `day` は最初に指定した日で、短い月は月末に丸める（31 日 → 2 月は 28 日）。
- 設定は、編集の窓の「繰り返し」（なし／毎週／毎月）。リストは設定済みを示す ↻ の印だけ（表の列を増やさない）。毎月は、期限の日を `day` に入れる。
- `changeStatus` で `Done` になったとき、`repeat` があれば次のタスクを 1 件作る。
  - 次の期限 = 周期の日付（毎月は旧期限の月から順に）のうち、旧期限と今日のどちらよりも後の最初の日。早く完了しても周期はずれず、遅れて完了したら、過ぎた周期は飛ばす。
  - 引き継ぐ: 件名・大項目・中項目・重要度・メモ・`repeat`・チェックリスト（全項目を未チェックに戻し、項目の ID は付け直す）。
  - 引き継がない: 前のタスク・待ち先・作業枠・開始日・完了日。状態は `To Do`。
  - `Cancelled` では作らない。
- 二重生成の防止: 元のタスクの `repeat.spawned` に次のタスクの ID を記録する。`Done` を戻して再度 `Done` にしたとき、その ID のタスクが残っていれば作らない。
- 共通作業は、利用者が「定例・共通」などのプロジェクトを作って置く。`init` は何も足さない。
- チェックリストの使い回しは、編集の窓の「複製」で行う。複製は、期限を今日にし、未チェックのコピーを、同じプロジェクト・グループに作る（`repeat` は引き継がない）。

## 守る制約

- 画面の保存は既存の保存と競合の仕組み（`sync.js`）を通す。履歴の追加も同じ編集の中で行う。
- 変更後に `npm run build` を実行し、`assets/task-trail.html` をコミットする。
- `docs/development.md` の対応する節（優先順位・日程変更・状態と進捗・ガントとリスト・設計判断）を、同じ作業で直す。
- 実ブラウザで確かめていないことは「未確認」と書く。

## 決めたこと（私の判断）

- ②の +40: 期限超過（+100）の下、重要度（+12）の上。実データでの使い心地は未確認のまま出す。
- ①の同日まとめと、合計 0 での削除。
- ③の `month` の `day` の丸め、`spawned` による二重生成防止、複製の期限を今日にすること。
- 繰り返しで作るタスクの期限は、休みの日でも動かさない。必要なら後から営業日への寄せを足せる。

## 検証の基準（実装時）

1. ①: 画面の期限変更で履歴が 1 件増え、同日に戻すと消える。原因を選ぶと保存される。依頼の帯の記録は変わらない。
2. ②: 予定日を過ぎた `Waiting` が「今日の優先」で上がり、予定日が空なら点数が変わらない。
3. ③: 毎週・毎月が、早い完了・遅れた完了・月末で正しい日付になる。`Done` の戻しで二重に作らない。チェックリストが未チェックに戻る。
4. `npm test` が通り、`npm run build` 後の差分が `assets/task-trail.html` に反映される。
