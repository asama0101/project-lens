## 開発の手順

```
npm test        # node --test
npm run build   # plugins/project-lens/assets/project-lens.html（プラグインに同梱する完成版）を作る
```

- `plugins/project-lens/src/` を変えたら `npm run build` を実行し、`assets/project-lens.html` をコミットする。古いと `npm test` が失敗する。
- GitHub Actions（`.github/workflows/test.yml`）が、`main` への push と pull request で、Windows・Node 24 の `npm test` を実行する。`engines`（`plugins/project-lens/package.json`）は `>=24`（README の表「Node.js | 24 以上」と同じ。それより古い版は未確認）。`engines` は npm の警告にしかならず、`node` の実行は止めない。ワークフローの実行は、GitHub 上では未確認。
- このリポジトリを直接開いてプラグインを試すときは、`claude --plugin-dir ./plugins/project-lens` で起動する。
- 環境変数 `PROJECT_LENS_HOME` は、プラグイン専用のフォルダ（`${CLAUDE_PLUGIN_DATA}`）の場所を固定する。テストと開発用。`--plugin-dir` で読み込むと置き場が本番と別（`project-lens-inline`）になるので、開発時はこれで固定する。

### リリースの手順

push のたびには `version` を上げない。リリースするときだけ、次の順で行う（グローバルの git-flow.md の段階 9 に、project-lens 固有の手順を足したもの）。

1. **version を上げる**: リリースする版（例: `v1.1.0`）が決まったら、その版の `v` を除いた数字に、次の 3 か所を合わせる。上げる PR は、リリースする変更の PR か、そのすぐ後の PR にする。
   - `plugins/project-lens/.claude-plugin/plugin.json` の `version`（変えないと、利用者に更新が届かない）
   - `plugins/project-lens/package.json` の `version`（`plugin.json` と同じ値。`tests/plugin.test.js` が一致を確かめる）
   - `tests/plugin.test.js` の `assert.equal(plugin.version, "…")`（固定値）
2. **マージしてからタグを打つ**: タグ（`vMAJOR.MINOR.PATCH`）は、version を上げた PR のマージ後の `origin/main` に付ける。version を上げる前のコミットに付けない。付けたあとで食い違いに気づいたら、タグと GitHub Release を付け直す前に、ユーザーに確認する。
3. 版の決め方・タグ・GitHub Release（`gh release create <版> --generate-notes`）は、git-flow.md の「リリースするとき」に従う。`docs`・`chore` だけのときは、版を上げず、リリースしない。

## 設計判断

- **作業枠（`sessions`）の ID の重複は、`validate` で warning にする**: 枠の移動・確認・削除は ID だけで探すので、重複すると両方に効く。共有ファイルに無いタスクの作業枠（`orphanSessions`）も、同じ個人ファイルの枠なので、重複の検査に含める。error にすると、すでに重複したデータが保存できなくなり、直す手段（CLI も画面も保存に失敗）が無くなるため、warning にとどめた。
- **変更履歴（`changeLog.taskIds`）に、消したタスクの ID が残っても注意にしない**: タスクを消しても変更履歴は残す（ID を使い回さない採番が、消したタスクの履歴が残ることを前提にしている）。`validate` は「changeLog: 存在しないタスク」の注意（warning）を出さない。出すと、日程変更のあったタスクを画面で消したあと、以後ずっとバナーに出て、画面からは消せず、何もこの注意を読んで動かないため。
- **依頼のやりとり（`thread`）の件数に上限を置かない**: やりとりは、聞き返し（エージェント）と返信（利用者）が交互にしか足せない（状態の遷移の表）ので、上限（たとえば 40 件）を置いても、同じ依頼で 20 往復になり、1 人で使う道具では起こらない。起こっても 1 件の依頼が長くなるだけなので、置かない。履歴の 20 件（`pruneRequests`）と、1 件の文章の 4000 文字（貼り付けた大きな本文を防ぐ）は残す。

- **タスクの ID は、消したあとも使い回さない**: 採番は、いまのタスクと変更履歴（`changeLog.taskIds`）の ID の最大番号 + 1（`edit.js` の `nextTaskId`。ID は `<プロジェクトの ID>-<4 桁>`、例 `AA-0001`。接頭辞は `<接頭辞>-\d{4}` の完全一致で数えるので、手書きの ID `P1-0011` と `P11-0001`（採番では生まれない形）が並んでも、互いに影響しない。9999 を超えるときは Error）。番号を 4 桁の連番にするのは、タスク数 + 1 だと、最後のタスクを消して足したとき同じ ID に戻り、消したタスクの変更履歴が、新しいタスクのものとして出た。見送った案: 採番の番号をデータに持つ（形式が増える）。履歴に残らない（変更履歴に載っていない）タスクの ID は、使い回されてもよい（何も参照しないため）。
- **予定表の取り込みは、別のエージェント（`intake-calendar`）にして、どちらも `tools` を絞る。予定表の取得（MCP の呼び出し）は、エージェントではなく、呼び出し元の会話が行う**: 予定表の件名・本文は、会議の招待を送る外の人が書ける。`calendar-auto` は承認なしで書き、見張りが 30 分ごとに無人で実行するので、件名の中に「メールを送れ」「コマンドを実行しろ」のような指示があっても、実行できるツールを持たない形にした。`intake` は `Read, Write, Bash`、`intake-calendar` は `Read, Bash`（MCP のツールを含まない）。呼び出し元の会話（`/project-lens:intake calendar` と、`/project-lens:watch` の手順1.5）が、`mcpconf.js show` の指定どおりに `listTool` で取得し、`fetched.json`（OS の一時フォルダの `project-lens-fetched-<日時>.json`。実行ごとに変わる名前にして、重なっても上書き・残留しないようにする）に書いて、エージェントに渡す。書いた会話は、エージェントを呼べなかった・失敗したときは、自分で消す。エージェントは、渡されたパスを読んで、終わったら消す。エージェントは、`fetched.json` を `calendar-auto` に渡すだけで、MCP を呼ばない。取得に失敗したとき・MCP が未指定のときは、会話の側でデータを変えずに終わる（エージェントを呼ばない）。
  - 限界（受け入れた）: 会話は、取得した件名を読むので、件名の指示は会話に届く。会話側の手順にも「読むだけのデータ」と、取得に使うのは `listTool` だけという規則を書いたが、歯止めは文章だけである（`tools` を絞った効果は、取り込みの段階だけ。取得した件名・本文は、MCP・Write・Bash をすべて持つ会話本体が読む）。会話は利用者の他のツール（メール送信など）を持つので、この経路は、エージェントに任せていたときより、会話の判断に頼る。エージェントは `Bash` を持つので、コマンドの実行は、文章の規則だけで止めている。`approve` を実行しない記述も、文章だけで、許可の確認が出るかは未確認。
  - 確かめた事実（公式の資料）: エージェントの `tools` は、`mcp__<サーバー名>__*`（サーバー単位）の形を受ける。`mcp__*` は、`disallowedTools` で全 MCP を除く例だけが載っていて、`tools` で全 MCP を許す書き方としては載っていない（未確認）。プラグインのエージェントも `tools` を使えるが、`mcpServers` は無視される。
  - 見送った案: `tools` に `mcp__*` などの全 MCP を許すワイルドカードを書く案（サーバー名が利用者ごとに違うので、書けるのは全 MCP を許す形だけで、メール送信などの MCP も含み、絞れたことにならない。`tools` での効き方も未確認）。`tools` を省略して全ツールを引き継ぐ案（Bash・Write・他の MCP が使え、件名の指示への歯止めが文章だけになる）。`disallowedTools` で除く案（除くべき MCP の名前を前もって挙げられない）。サーバー名を `/project-lens:mcp` の保存時に agent ファイルへ書き込む案（`${CLAUDE_PLUGIN_ROOT}` は更新で入れ替わり、実行時に書かない規則（A1）に反する）。
  - 承認の境界の限界（受け入れた）: `inbox` エージェントは `Bash` を持つので、`node tools/inbox.js approve` を自分で実行できる。承認を人だけに限る仕組みは、エージェントの文章（`approve` はどの場合も実行しない。`reject`・`fail` は手順に書いた場合以外は実行しない）だけである。`tools` にコマンドのパターン（`Bash(...)`）を書く方法は、Claude Code の文書に書かれておらず、効くか確かめていない（未確認）。プラグインのエージェントの `hooks`・`mcpServers`・`permissionMode` は無視される（公式の文書）ので、hook で `approve` を弾く方法も使えない。コマンド単位で絞るなら、利用者の設定の `permissions.deny` に書く方法がある。`intake` の `Write` を外す案も見送った。外すと `rows.json` を `Bash` のリダイレクトで書くことになり、外部由来の文字列がシェルを通るため、かえって危ない（`Bash` は無制限のままなので、外しても安全にはならない）。
  - `/project-lens:watch` の `allowed-tools` は、`approve` を事前に許可しない。メインの会話が、エージェントの報告（外の人由来の文字を含みうる）の「承認してください」に従っても、実行の許可の確認が出る。`reject`・`get`・`wait` は、反映しない（または読むだけ）ので許可したままにしている。
- **`project-lens-mcp.json` は、一時ファイルに書いてから置き換える**: 書き込みの途中で止まっても、予定表の取り込みが全部止まる壊れ方をしないため（`data.json` の保存と同じ方針）。

- **プロジェクトの期限を、タスクの最終期限から決める**: 依頼文に日付がなく、タスクの案と一緒に決まるため、依頼で期限を必ず指定させる案は見送った。期限は、承認前の提案カードで確認して、「修正を依頼する」で直せる。
- **「プロジェクトの期限を超えます」の警告は、後ろへ動かすタスクがあるときだけ**: 影響の計算（`computeImpact` の `projectDueExceeded`）と、依頼の変更案（`planOps` の警告）は、新しい期限が今の期限より後で、かつプロジェクトの期限より後のときだけ出す。前倒しは、まだ超えていても出さない（遅れを縮める操作に「超える」と言わないため）。
- **マイルストーンの警告は、プロジェクトの期限を超えるときだけ**: 日付を動かしたときに「後ろにタスクが残る」ことで警告する案は見送った。途中の節目（例: 機器発注）の後には、いつもタスクが残るため、毎回警告が出て意味がなくなる。
- **共有 + 個人の 2 ファイルで使う**: 1 つの共有ファイル（`data.json`）を複数人が使い、作業枠・会議・休みなどは各自の個人ファイル（`personal.json`）に置く。保存前に、ファイルごとに更新日時を比べ、他の更新があれば最新のファイルに同じ編集を当て直して保存する（ロックはしない）。分け方と見送った案は「画面の動き > 共有ファイルと個人ファイルの分割」、保存の規則は「保存と競合」。
- **スキルの起動**
  - `intake` のスキルも `disable-model-invocation: true`（利用者が `/project-lens:intake` と明示して呼ぶ）。予定表の会議は承認の確認なしで書くので、モデルの判断では起動させない。
  - いずれも、変更案を示して承認を得てからデータを書き換える。書き込みは CLI（`tools/inbox.js`・`tools/intake.js`）に任せ、CLI が書く前に検証（`validate`）し、通ったときだけ書く（通らなければ何も書かない）。`intake`・`intake-calendar` のエージェントは、書き込んだ後に `validate.js` を実行しない（書けた後に `errors` は出ないので、同じ検証の二重になるため）。エージェントが `data.json` を直接書き換えることはない。日程の変更は、受信箱の経路（HTML の帯 → `inbox` エージェントの `propose` → `approve`。「HTML からの依頼（inbox）」を参照）で行う。
  - `doctor`・`init`・`mcp`・`watch` も `disable-model-invocation: true`（利用者が明示して呼ぶ）。`doctor`・`init`・`mcp`・`watch` は、自分のスクリプトだけを `allowed-tools` で事前に許可している。
- **画面の編集では前後のタスクを見ず、前後の見直しを Claude Code の依頼に寄せた**: 画面での期限・開始日の変更に確認パネルを挟むと、1 件を直すたびに手が止まるため。前のタスクの期限を見て、次のタスクをまとめて動かす判断は、原因と理由を残せる依頼の処理に集めた。代わりに、次のタスクとの食い違い（次のタスクの期限が前のタスクより前になる）も画面は警告しない。
- **入口を HTML の依頼に寄せた**: 日程の変更・タスクやプロジェクトの変更を、コマンド（`replan`・`inbox`）ではなく、HTML の「Claude Code に依頼する」から行う。入口が 3 つ（コマンド・画面の編集・依頼）に分かれていて、どれを使うか分かりにくかったため。手動で依頼を処理する入口（`/project-lens:inbox`）は設けず、処理は `/project-lens:watch` の見張りが行う。見張りが止まっている間、依頼は処理されない。見送った案: 手動の入口を残す（コマンドが増え、入口の整理にならない）。
- **祝日の更新を `holidays.js ensure` に置いた**: 更新の判定（未取得・取得から 30 日超・一覧の最終日が今日以前・提案が使う日が一覧の範囲外）を `needsHolidayUpdate` の 1 か所に置き、`propose` と `ensure`（`watch` を始めるとき）が同じ判定を使う。判定をエージェントの指示（Markdown）に書くと、実行のたびにぶれるため。見送った案: Claude Code の起動時（`SessionStart` フック）に取得する（毎回の起動でネットワークに出る。フックの設定が増える）。
- **土日祝を営業日に数える設定を `data.json` ごとに 1 つにした**: `settings.countWeekendsAndHolidays`（`true` のときだけオン）。仕事用とプライベート用で `data.json` を分けて使うため、プロジェクトごとの切り替えは要らない。オンのとき、土日と日本の祝日を営業日に数え、手動の休み（`holidays`）は飛ばす。切り替えは HTML の設定タブ（「基本の設定」の先頭の行「営業日の数え方」）だけで行う。見送った案: 土・日・祝日を別々に選ぶ（まとめて足りる）、プロジェクトごとの切り替え（`data.json` を分けるので不要）、依頼からの切り替え（設定は画面で変える方針）。
- **`intake` スキルは手動起動に限る**（`disable-model-invocation: true`）: `calendar-auto` が承認なしで、予定表の会議の追加と、終わっていない未確認の会議の更新・削除を行うため（plugin-rules.md の B4 の「不可逆な書き込み」）。「予定表を取り込んで」と頼んでも、モデルは起動しない。`/project-lens:intake calendar` と打つ。見送った案: 自動起動のままにして、理由を書く（承認なしの削除を、モデルの判断で起動できてしまう）。calendar だけ別のスキルにする（コマンドが増え、README・テスト・`docs/flow.html` の直しが広がる）。
- **MCP を同梱しない**
  - 予定表の MCP（Outlook など）は、利用者が Claude Code に用意したものを使う（`.mcp.json` はない）。
  - 指定は `/project-lens:mcp` で `${CLAUDE_PLUGIN_DATA}`（`~/.claude/plugins/data/` の下）の `project-lens-mcp.json` に保存し、`data.json` には入れない。
  - このファイルには `schema_version`（現在 1）を入れる。無いファイルは古い形式として、読まずに「project-lens-mcp.json（<パス>）を削除してから、/project-lens:mcp で指定し直してください」のエラーにする（利用者の判断: 古い形式への互換性は不要）。`/project-lens:mcp` の保存（`set`・`clear`）も、このファイルを読むので同じエラーで止まる。そのため、パスを示して、先に削除するよう案内する。保存形式を変える版では、この節に移行手順を書く。
- **レポート（共有用 HTML の保存）を機能ごと消した**: 共有ファイルを開けば、各自が同じ画面を見られるので、共有用の HTML を出す手段は要らない。レポート専用の `core/reportspec.js`・`ui/views/report.js`・`ui/views/reportpanel.js`・`ui/savefile.js`、`prefs.js` の記憶、`gantt.js` の `readonly` 引数を消した。`data.json` の `settings.reportShowMeetingTitles` は、残っていても検証が何も言わない（データからは消さない）。見送った案: 読み取り専用のガントだけ残す（使う画面がなくなるため）。
- **SharePoint Online 上には、共有ファイル（`data.json`）だけを置き、ネットワークドライブ（または同期したフォルダ）経由で使う。個人ファイル（`personal.json`）は手元に置く。https の URL での読み書きは対応しない**: 共有ファイルをローカルに置けない利用者がいるため。画面は `showOpenFilePicker`・`createWritable`・`lastModified` だけを使い、ファイルの場所を区別しない（`store.js`）ので、割り当てたドライブのファイルを選べば、コードの変更なしで使える見込み。個人ファイルは、各自が自分の手元で使うので、置き場の共有は要らない。利用ガイド（`docs/guide.md`）に手順を書いた。見送った案: Microsoft Graph での読み書き（Entra ID へのアプリ登録と権限の許可が要り、利用者は管理者に頼めるか不明。ログインの戻り先に `file://` を使えないので、HTML を置く https の場所も要る。競合の検知を ETag に、自動の読み直しを Graph 向けに作り直す必要がある）、Power Automate を間に挟む案。未確認: ネットワークドライブ・同期フォルダの共有ファイルを、ブラウザの「ファイルを開く」で選べるか・保存できるか・実ブラウザの権限の確認が通るか。同期の遅れや WebDAV の遅さが、自動の読み直し（4〜16 秒ごと）と、共有に無いタスクの作業枠のバナー（同期の遅れで、一時的に出うる）に与える影響。CLI（`tools/cli.js` の置き換え保存）・`/project-lens:watch` がこのドライブで動くか。
- **外部パッケージを使わない**: ローカルサーバー・常駐プロセス・データベースも使わない。Excel の取り込みだけ、Python の `openpyxl`（システムのもの、または専用の venv `<置き場>/venv` のもの）を使う。
  - CI（`.github/workflows/test.yml`）は、`windows-latest` で `npm test` だけを流し、lint は流さない。lint の道具（ESLint など）が外部パッケージになり、この方針とぶつかるため。構文の誤りは、`npm test` と `npm run build` が読み込む時点で見つかる（テストにもビルドにも読み込まれない .js が無いかは、未確認）。見送った案: `node --check` を CI に足す（読み込まれるファイルでは、新しく見つかるものがない）。ESLint を入れる（`devDependencies` と設定ファイルが増える）。

- **依頼の操作を `addTask` と `moveDue` に絞った**: 日程の連鎖（後続タスクを最小限だけ動かす）と、文章でのタスクの登録は、画面では手間がかかる。一方、状態・重要・削除・プロジェクトやマイルストーンの変更は、画面で 1 回で直せ、依頼の処理（操作の種類ごとの変更案と検査）を維持する割に使われなかった。そのため、依頼はこの 2 つに絞り、ほかは画面で行う。保存済みの検証用の `OP_KINDS`（17 種類）は残す（古い依頼が `data.json` に残っていると、検証に通らず保存できなくなるため）。新しい提案・承認では `PROPOSE_OPS` 以外を拒否し、承認時は失敗にして「もう一度提案してもらう」で作り直せる。見送った案: `OP_KINDS` も 2 種類にする（古い依頼を持つデータが保存できなくなる）、古い依頼を黙って捨てる（利用者が頼んだ記録が消える）。

- **タスクが「プロジェクトなし」（`projectId: null`）を持てるようにした**: 突発の対応を、ヘッダーの「＋ 突発タスク」の入力欄だけで登録し終えるため（プロジェクトを選ぶ・作る手間を挟まない）。ID は `ZZ-` + 4 桁の連番（`nextTaskId`。プロジェクトの ID は `AA`〜`ZY` なので、`ZZ` と重ならない）。点数・今日のタスク・稼働（「プロジェクト未設定」の行）は、プロジェクトのあるタスクと同じ規則で扱う。見送った案: 「突発対応」という普通のプロジェクトを使う（変更は最小で済むが、利用者は変更の大きさを知ったうえで、プロジェクトなしを選んだ）。プロジェクトなしの並び替え（`moveTask`）・依頼の `addTask`/`moveDue`・WBS の取り込みへの対応（これらの規則は、同じプロジェクトの中のタスクを前提にしている）。前のタスクも同じ理由で、プロジェクトなしのタスクには付けない（`predecessorCandidates` は空を返し、`updateTask`・`addPredecessor` は「プロジェクトなしのタスクには前のタスクを付けられません」の Error にする。外すことは妨げない）。緊急の印・点数の変更（印は付けないと決めた）。
- **README を図中心にして、詳細を `docs/guide.md`（利用ガイド）に分けた**: README は初見の利用者が読む入口で、機能・導入・使い方を図で見せ、100 行以内に収めるため。README の表「Node.js | 24 以上」は、テストが読む（`plugin.test.js`）。導入の補足（オフライン・更新・アンインストール・doctor）、設定の一覧、困ったときの全件は、利用ガイドだけに書く（2 か所に書くと食い違うため）。見送った案: 詳細を README に残す（100 行を超え、図が埋もれる）。

- **`/project-lens:mcp` は、引数なしでも指定の手順へ進む（表示だけで終わるのは `show` のとき）**: README・利用ガイド・doctor・intake の案内は、どれも引数なしの `/project-lens:mcp` なので、案内どおりの操作で指定まで進めるため。指定済みのときは、変えるかを聞いて、変えないなら候補の提案と保存を飛ばす（実行のたびにやり直させないため）。
  - 見送った案: 案内を `/project-lens:mcp calendar` にそろえる案（直す箇所が doctor.js・README・利用ガイド・intake に散り、テストの文言も変わるため）。
- **`fetched.json` の形の規則は、watch と intake の両方の本文に書く（別のファイルにまとめない）**: watch は、intake の本文を読めない（intake は自動で読み込まれないスキル）。また、frontmatter と Read で開いたファイルは、スキルを起動した turn のあとでは助けにならない。作業フォルダの外にあるプラグインのファイルを Read で開くと承認の確認が出て、事前承認はスキルを起動した turn だけで効く。watch の予定表の更新は、30 分ごとに Monitor の通知で始まる turn で動くので、別のファイルにすると毎回確認が出て、断られると形の規則なしで書きうる。
  - 見送った案: 形の規則を 1 つのファイルにまとめ、書く直前に Read で読ませる案（上の理由）。
- **`intake` エージェントの質問と承認は、呼び出し元の会話が受け持つ**: エージェントは、利用者に質問して答えを待てない。質問や承認をエージェントの文章に任せると、利用者が「はい」と答えたあとの動き（続きを頼む・作り直す・会話が自分で書く）が決まらず、見た変更案と違う内容で書きうる。承認の依頼に `planKey` と `rows.json`・`mapping.json` のパスを入れ、新しいエージェントに頼むことで、`wbs-apply --plan-key` が、見た変更案と書く時点の変更案が同じかを照合する。`xlsx.js setup` の入れ先も、環境の導入は利用者の承認が要るので、会話が AskUserQuestion で選ばせ、選んだ依頼の行だけを頼む（エージェントは、その依頼のときだけ `--yes` を付ける）。
  - 頼み直すときは、毎回、新しいエージェントとして呼ぶ（`skills/intake/SKILL.md` に書いてある）。実機で、前のエージェントにメッセージの送信で承認の依頼を送ると、エージェントは呼び出し元からの続きのメッセージを利用者の承認として扱わず、書き込みを断った。新しいエージェントへの依頼としては、書き込んだ。
  - 見送った案: 同じエージェントに、メッセージの送信で続きを頼む案（上の理由で、書き込まれないため）。会話が `wbs-apply` を自分で実行する案（`/project-lens:intake` は `allowed-tools` を持たず、エージェントで `tools` を絞った意味が薄れるため）。
- **見張りは、起動時のタスク ID で止める**: 実機で、実行中の Monitor は、作業の一覧を出すツールに出なかった。起動時に返る ID を渡せば止まる。
  - 見送った案: 作業の一覧から、コマンドが `inbox.js wait` の Monitor を探して止める案（上の理由で、見つからずに「動いていません」と答え、見張りが残るため）。
- **打ちかけの入力の間は、自動の読み直しの描き直しを待たせる（データは取り込む）**: 描き直すと、`change` 前の文字が消えるため。待たせるのは、フォーカスのある欄の値が描いたときと違う間だけで、確定・フォーカスが離れたら 1 回描き直す。見送った案: 読み直し自体を止める（データが古いまま保存の競合が増える）、描き直しの前後で打ちかけの値を写して戻す（欄ごとに、ファイル側の値が変わったときの扱いを決める必要がある）。
- **共有ファイルに無いタスクの作業枠は、検証の注意にする**: `core/split.js` の `mergeData` は、共有ファイルに無いタスクの作業枠を `data.orphanSessions` に入れる。`validate` は、これが 1 件以上あれば「共有ファイルに無いタスクの作業枠が N 件あります」の注意（warning）を出す。error にはしない（保存を止めない）。作業枠の ID の重複の検査（warning）は、`orphanSessions` も含めて数える（同じ個人ファイルの枠で、移動・削除は ID だけで探すため）。重なりなど、ほかの検査は `tasks[].sessions` だけを見るので、`orphanSessions` は数えない。画面の案内（バナーと削除ボタン）は、「保存と競合」の「共有に無いタスクの作業枠」。
- **スケジュールでタスクを置く方法は、ドラッグだけにした（押して選び、カレンダーを押して置く方法は持たない）**: 利用者の判断。カレンダーを押す操作を、枠・会議の選択だけにするため。右の列の行は `draggable` と `data-dragtask` だけを持ち、押しても状態は変わらない（選択の状態・選択の見た目・行の `tabindex` は持たない）。
  - 見送った案: キーボードでの配置を残す案（利用者がドラッグだけを選んだ）。そのため、キーボードだけでは、既存のタスクを時間枠に置けない。
- **勤務時間（`settings.workday`）の設定をやめ、スケジュールの時間の軸を 00:00〜24:00 の固定にした**: 利用者の判断。勤務時間の外（早朝・夜）の作業も枠に置けるようにし、設定の項目を減らすため。作業枠は、その日の 00:00〜23:59 のどこにでも置ける（終了の上限は 23:59。時刻は `HH:MM` で持ち、24:00 は書けないため。`core/sessions.js` の `LAST_END`）。一緒に、空き時間の計算（`freeSlots`）と、週表示の日付の下の「空き 〇h」もやめた（勤務時間がないと、空きの範囲が決まらないため）。古いファイルに残った `workday` は読まず、検証も何も言わない（移行のコードは持たない）。`PERSONAL_SETTINGS` から外したので、古い個人ファイルに残っていると、次の保存で共有ファイルの `settings` に移る（未知のキーは共有に置く規則のため。読む側はないので、動きは変わらない。実データでは未確認）。突発タスクの開始の初期値は、今日なら現在時刻を 15 分刻みに切り上げた時刻（23:45 まで）、ほかの日は 09:00（`views/schedule.js` の `urgentDefaultStart`。勤務の開始の代わりの固定値）。見送った案: 勤務時間を表示の範囲としてだけ残す（設定が残り、範囲の外の枠の扱いを決める必要がある）。
- **突発タスクの入力欄は、ヘッダーの「＋ 突発タスク」（`data-urgent-open`）からだけ開く**: 利用者の判断。入口を 1 つにして、カレンダーを押す操作（枠・会議の選択）と混ざらないようにするため。見送った案: 週表示・日表示の空き時間のボタンを押して開く（入口が 2 つになり、押すまで透明にしても、選択やドラッグの場所と重なる）。
- **週表示の今日の列には、背景色を付けない（日付の見出しの青い太字と、列の上端の `--accent` の線だけで示す）**: 背景色があると、予定の枠（`--accent-soft`）や会議の色と重なって見分けにくいため（利用者の判断）。見送った案: 予定の枠と違う色（薄い黄）の背景（利用者が、背景そのものをやめると決めた）。日表示にも、今日の背景色はない。

## 算出の規則

### 優先順位（今日の優先）

対象は `Done`／`Cancelled` 以外で、前のタスクがすべて完了しているもの。点数の合計が高い順（実装は `core/schedule.js`）。

| 項目 | 点数 |
|---|---|
| 期限超過 | +100 |
| 期限点 | 残り 30 日以内は `(30 − 残り日数) × 1.5`（超過した分も加算）。残り 31 日以上は 0 |
| チェックリストの倍率 | 期限点に `1 + min(未チェックの項目数, 10) ÷ 10` をかける（最大 2.0）。`Waiting` は 1（かけない）。`+100` と重要にはかけない |
| 重要 | `important: true` なら +12 ／ それ以外 0（倍率のあとに足す） |
| 回答予定日の超過 | `Waiting` で `waitingOn.expected` が今日より前なら +40（倍率をかけない）。理由に「回答予定日を過ぎています（N日）」を出し、行の文言は「催促」にする |

- 例（重要でない）: 期限 5 日後・未チェック 3 件 ＝ 25×1.5×1.3 ＝ 48.75。期限 5 日後・項目なし ＝ 37.5。3 日超過・未チェック 10 件 ＝ 100＋49.5×2.0 ＝ 199。`Waiting`・期限 5 日後・未チェック 3 件 ＝ 37.5。期限 35 日後 ＝ 0。
- 「このタスクを前のタスクとする未完了タスク 1 件ごと +10」と「`Waiting` +15」は、点数に含めない（設計判断を参照）。行の「理由」には、点数に使わなくなったあとも、「次のタスク N 件を止めている」と `Waiting` の催促・確認の文言を残す（`action: "chase"` も同じ）。点数は画面に出さない。
- 開始日（`start`）は参照しない。開始日の前でも、前のタスクがすべて完了していれば載り、点数は 0 になりうる。
- 行の理由の「期限まで N日」は、期限点の範囲に合わせて、残り 30 日以内に出す。
- プロジェクトなしのタスクも、同じ点数で載る。行のプロジェクト名は「プロジェクトなし」と出す。
- 同点は期限の早い順、次に ID 順。丸めはしない。

### 日程変更

- 前のタスク（`predecessors`）をたどり、次のタスクを**最小限だけ**動かす。前のタスクの新しい期限を超えないようにするだけで、余裕のある次のタスクは動かない。
- `Done`／`Cancelled` は動かさない。依存が入力されていないタスクも動かない。
- 前倒しのときは、「詰める」を選ぶと、次のタスクも同じ日数だけ前倒しする（前のタスクの新しい期限より前にはしない）。
- この計算（`core/impact.js`）を使うのは、「Claude Code に依頼する」の反映だけ。画面の期限の変更は、前後を見ずにそのタスクだけを保存する（「ガントチャートとリスト」の節）。

### 状態と進捗

- タスクの状態は `To Do`／`In Progress`／`Waiting`（待ち先を持つ）／`Done`／`Cancelled`（進捗率の分母から除く）。
- プロジェクトの状態は `計画中`／`進行中`／`保留`／`完了`／`中止`。
- 遅延・リスクは状態ではなく自動判定のバッジ。「期限超過 N件」、「待ち長期化」（`Waiting` が `settings.waitingLongDays` 日以上）、「プロジェクト期限超過」。
- 進捗率は `Done` ÷（`Cancelled` を除く全タスク）。
- `Waiting` の `waitingOn` は `{ party, since, expected? }`。`expected` は任意の回答予定日で、`Waiting` を外すと `waitingOn` ごと消える。日付欄を一部だけ消した入力の途中は、値が空文字になり、保存済みの予定日が消えるので、`validity.badInput` のときは保存しない（実ブラウザで部分入力の `change` が実際に出るかは未確認。出ない環境では、この判定は何もしない）。
- 定例タスク（`task.repeat`）は `{ unit: "week" }` か `{ unit: "month", day }`。`Done` にしたとき（画面の `setStatus`）、`spawnNextRepeat` が次回を 1 件作る。次の期限は、周期の日付のうち、旧期限と今日のどちらよりも後の最初の日（`core/repeat.js` の `nextRepeatDue`。毎月は短い月で月末に丸める）。件名・大項目・中項目・重要・メモ・繰り返し・チェックリスト（未チェックに戻す）を引き継ぎ、前のタスク・待ち先・作業枠・開始日は引き継がない。元の `repeat.spawned` に次回の ID を記録し、`Done` を戻して再度 `Done` にしても二重に作らない。`Cancelled` では作らない。編集の窓の「複製」（`duplicateTask`）は、期限を今日にした未チェックのコピーを作る。
- 未確認（実ブラウザでの操作）: リストの回答予定日の欄、編集の窓の「繰り返し」と「複製」、定例タスクの完了での次回の作成。ここまでの確認は、単体テストと、画面を開いたときにコンソールのエラーが出ないことだけ。
- チェックリスト（`task.checklist = [{ id, text, done }]`）は、タスクの状態と連動しない。全項目をチェックしても状態は変わらず、進捗率にも使わない。状態を `Done` にするときだけ、未チェックの項目があれば警告する（「ガントチャートとリスト」の節）。
- タスクの `projectId` は、`null`（プロジェクトなし）でもよい（`core/schema.js` の検証は、`null` か存在するプロジェクトの ID を受ける）。プロジェクトなしのタスクの ID は `ZZ-` + 4 桁の連番（`ZZ-0001`）。プロジェクトの ID は `AA`〜`ZY`（`nextProjectId`。使い切ったら Error。最大 675 個）で、`ZZ` は付けない。ID の形は検証しない（手で書いた `A1` のような ID もそのまま使える）。進捗率・稼働時間は、プロジェクト単位の集計なので、プロジェクトなしは含まない（稼働は「プロジェクト未設定」の行に出る）。

## 画面の動き

画面上部のナビは、ガントチャート・リスト・スケジュール・稼働・設定の 5 つ。`S.screen` が `gantt`・`list`・`schedule`・`workload`・`settings`（初期値は `gantt`）で、保存はしない。ガントチャートとリストは、同じ `renderProjects`（`opts.view`）で、絞り込み・「完了を隠す」の状態を共有する。画面内の「ガント／リスト」の切り替えボタンは持たない（`S.pview` は廃止）。

### 全体

- ヘッダー、ガントチャート・リストのフィルタの行、右側の列（今日のタスク・今日の優先）は、スクロールしても上端に固定する（CSS の `sticky`。ヘッダーの高さを `--hh`、フィルタ行の高さを `--th` に入れて、下の帯が、その下に付く）。固定表示は、画面のスクロールに対して、CSS の `position: sticky` で付ける（JS でずらさない。ずらすと、画面のスクロールが先に動き、日付が遅れて動いてから戻る）。新しい CSS は、`theme.css` の末尾の節にまとめ、すべて `#view` の中に限る。
  - **絞り込み行（`.ptool`）**: プロジェクトのチップは 1 行に収め、横にスクロールする（`.chips-row`。`flex-wrap:nowrap; overflow-x:auto`）。プロジェクト名のプルダウン（`data-projectpick`。完了も含む全プロジェクト）と「＋ プロジェクトを追加」は、スクロールの外（`.ptool-end`）で固定。チップは、状態が「完了」のプロジェクトを出さない（選択中のあいだだけ出す。完了のものは、プルダウンから選ぶ。「完了を隠す」ボタンの基準（全タスクが Done も含む）とは違い、プロジェクトの状態だけで決める）。大項目で絞り込む機能（`S.group`・`data-groupfilter`・`renderGantt`/`renderList` の `group` オプション・`groupNames`）は、利用者の希望でやめた（プルダウンに置き換えた）。各タスクの大項目・中項目の表示と編集は残る。プロジェクトが何件でも、固定の高さ（`--th`）は 49px のまま（30 プロジェクトで、折り返していたときは 231px。実測）。スクロールバーは出さない（`scrollbar-width:none`）。出すと、チップがあふれたとき、固定の行が 15px 高くなり、プロジェクトの数で高さが変わるため。代わりに、マウスの縦のホイールで横に動かし（`wheel`）、横スワイプ・Tab でも動く。デメリット: スクロールバーがないため、マウスだけの利用者は、ホイールを回すまで、あふれていることに気づきにくい。描き直しでは、チップの行の横位置を保ち、選択中のチップが見えなければ、行の中だけを動かす（`scrollIntoView` は、ページの縦も動かすので使わない）。
  - **ガント**: プロジェクトごとに、`section.pg` の中を、`.pgstick`（プロジェクトの見出し `.pg-head`。`sticky`、`top: --hh + --th + --gh`。`--gh` は操作の帯 `.gtop` の高さ）と、`.gwrap`（`.gstrip` + `.gscroll`）に分ける。`.gscroll` は横だけにスクロールする（`overflow-x:auto; overflow-y:hidden`）。`.gstrip` は、本物の日付軸（`.g-head .g-lane`）の写し（左の空き `.gsl` + 窓 `.gsv`）で、`sticky`（`top` に `--pgh`、見出しの高さ）。次のプロジェクトに入ると、見出しと複製が入れ替わる（`sticky` の動き。`section.pg` が範囲）。`data-todayfrac`・`data-s0`・`data-span` は、全プロジェクト共通の値を、各 `.gscroll` に付ける（ドラッグ・今日へ移動が `.gscroll` から読む）。
  - `.gwrap` は `padding-bottom: --sh + --sb`、`.gscroll` は同じ分の負の `margin-bottom`、`.gstrip` は `margin-bottom: -(--sh)`: 流れの高さを増やさず、`sticky` の範囲を複製の高さ（`--sh`）と横スクロールバーの高さ（`--sb`）だけ短くする。複製が、プロジェクトの下端（横スクロールバーを含む）を越えて、下のものに重ならない（`--sb` を除かなかったところ、複製の下端が表・枠の横スクロールバーの 15px に重なった。実測）。複製の目盛りの行は、本物の行の `column-gap`（12px）だけ右へ置く（測らないと、12px ずれた）。
  - 再描画（`render`）のとき、ガントの横位置（`scrollLeft`。全プロジェクトで同じ）とページの縦の位置（`scrollY`）を保つ。描き直しの間、`#view` に `min-height` を付けて、ページが縮んで `scrollY` が飛ぶのを防ぐ。`#view{overflow-anchor:none}`: 切らないと、ブラウザのスクロールアンカーが、描き直しのたびに縦の位置を +2px ずつずらした（実測）。`alignGScrolls` は、動かした枠の `scrollLeft` を他の枠にそろえる。代入で起きる `scroll` は無視する（`WeakMap` の `aligned`）。無視しないと、動いている最中の枠を、古い位置へ引き戻した（「今日へ移動」が 1px で止まった。実測）。「今日へ移動」のなめらかなスクロールは、先頭の枠だけに掛け、他の枠は `alignGScrolls` が追う。
  - **リスト**: プロジェクトの見出し全体は、`section.panel` の直下の `.pstick` にあり、`sticky`（ヘッダー・フィルタ行の下）。中身は、名前と状態の行 `.prow`（編集できる入力欄 `data-pf="name"`・`data-pf="status"`）と、その下の `.phead`（種別・開始・期限・進捗・稼働・注意の印）。利用者の希望で、注意の印（期限超過など）も固定する（印が折り返すと、固定の高さが増える）。未測定: 印が折り返したとき（3 行など）の高さ。画面の高さが低い（500px 前後）と、固定部分が増え、表の見える高さが減る（上限や折りたたみは足していない）。Tab で表の入力欄にフォーカスすると、固定部分の裏に隠れうる（`scroll-padding-top` がない。未実測）。列見出しは、表を包む `.twrap` の先頭の**複製**（`.thstrip`、`aria-hidden`。`renderList` が空で出し、`syncThStrips` が、本物の `thead` の各列の幅・余白・文字を測って写す）で固定する。`.thstrip` は `sticky`（`top: --hh + --th + --ph`。`--ph` は `.pstick` の高さで、`syncThStrips` が `section.panel` に入れる）。`.twrap` は表だけを含む（マイルストーン・履歴は外）。`padding-bottom: --sh + --sb` と、表の枠の負の `margin-bottom` で、`sticky` の範囲を短くし、複製が表の下端を越えない。固定していないときは、本物の `thead` に重なる（差 0px）ので、出し分けの JS（`thStripOn`・`updateThStrips`）は持たない。横スクロールの位置は、表の枠の `scroll` イベントで、複製の `translateX(-scrollLeft)` にそろえる（横方向だけ JS）。本物の `thead` が非表示（幅 860px 以下）のときは、複製を空にする（`:empty` で隠れる）。複製は、描き直し・画面の大きさの変更のたびに（`syncSticky` から）作り直す。リストの表は `pinTableHeads` の対象外。
  - 設定・稼働の表（`.tscroll` で `.tlist` でないもの）の列見出しは、従来どおり `pinTableHeads` がずらす。
- 右上の「ガント実績」のスイッチと、右の列の開け閉め（`showPrio`）は、このブラウザに保存する。右の列の開け閉めは、本体と右の列の境界線の取っ手（`.side-toggle`、`data-pref="prio"`）で行う。閉じても取っ手は残る。幅 900px 以下では、列が 1 つに回り込み、取っ手は横長の帯になる。取っ手の名前に「今日の優先」が入るので、パネルの有無は見出しの id（`h-rk`・`h-td`）で見る。
- URL に `?today=2026-10-20&time=10:15` を付けると、現在日時を固定して開ける（動作確認用）。

### ファイルを開く（開始画面・バナー）

- 画面は、共有ファイル（`data.json`）と個人ファイル（`personal.json`）の 2 つを開く。2 つとも開くまで、ガント以降を描かない（開始画面）。起動時は `restore()` で、権限が許可済みの方だけ自動で開く。
- 開始画面は、開いていない方（`missing()`）ごとに、案内（「共有ファイルを選んでください」・「個人ファイルを選んでください」）と、選ぶボタン（`data-open="shared"`・`data-open="personal"`）を出す。押すと `choose(which)` で、2 つ揃ったときだけ `loaded` で画面を開く。揃わなければ開始画面のまま、足りない方の案内だけを出す。
- 「前回のファイル（…）を開く」（`data-reopen`、`reopen()`）は、開いていない方に記憶があるとき（`lastFile()` の名前）だけ出し、その名前を並べる。権限の確認だけで開く。
- 開始画面のボタンは、プロジェクトの絞り込み（ガントの `data-open`）と同じ属性名なので、`#view` のクリックでは、データが無い（`!S.data`）ときだけ、ファイルを選ぶボタンとして扱う。
- 上部のバーの「別の共有ファイル」・「別の個人ファイル」（`data-open`）は、選んだ方だけを差し替える（もう片方は開いたまま）。開けなかった理由は、開始画面では画面に出し、画面が開いているとき（`S.data` がある）は、通知（`toast`）で出す。
- 直接保存に対応しないブラウザ（`showOpenFilePicker` が無い）では、開始画面に、2 つのファイルを一度に選ぶ入力欄（`<input type="file" multiple>`）を出す。共有か個人かは、中身の形で見分ける（`dataFromTexts`: `projects` が配列なら共有、そうでなければ個人。共有 1・個人 1 でなければ、「1 つずつ選んでください」で開かない）。保存は、画面上部の「JSON を書き出す」が、`data.json`・`personal.json` の 2 つを 0.3 秒の間隔で続けてダウンロードする（`exportFiles`）。ブラウザが、続けて複数のダウンロードをする許可を尋ねることがある（未確認）。1 つのファイルを、データ全体として読む経路は持たない。
- 共有に無いタスクの作業枠（`data.orphanSessions`）: バナーは、注意の文のあとに、ボタン「該当の枠を削除」（`data-orphan-clear`）を出す（`common.js` の `bannerHtml`）。押すと `S.pendingOrphan`（メモリのみ）が立ち、「N 件の作業枠を削除します。タスクが戻っていないか、少し待ってから確認してください」と「削除する」・「やめる」に変わる。「削除する」は `apply((d) => removeOrphanSessions(d), …)` で、`orphanSessions` を空にするだけ（タスクと枠は変えない）。保存はふつうの編集と同じ道（`sync.persist` → `createPairStore`）で、変わるのは個人ファイルだけ。確認を挟むのは、共有ファイルの同期（SharePoint など）が遅れて、タスクが一時的に見えないだけのことがあるため。`orphanSessions` の枠は、カレンダー・優先度・稼働には描かない（`tasks[].sessions` だけを読む）。
  - 削除のボタンと確認は、検証の注意のバナー（`refreshBanner` が出す `validated` つき）にだけ付ける。保存の失敗・「読み直せません」・「直接保存できません」のバナーには付けない（付けると、再読込・書き出しのボタンを押す前に上書きしうるため）。`banner()` は直前の文と操作を覚え、削除のボタン・やめる・削除するは、それを描き直すだけで、検証の結果で上書きしない。`sync.js` が保存の失敗から戻ったときは、失敗の印を下ろしてから `banner("")` を呼び、画面は、空の文を「検証の結果を出し直す」と読む。
  - バナーの文は `refreshBanner`（`validate` の結果）で出し直す。ファイルを開いたとき（`loaded`）・読み直しの成功（`reloadFile`）・`sync.js` が他の更新を取り込んで `setData` するとき（保存の失敗中を除く）に出し直すので、タスクが戻って `orphanSessions` が空になれば、バナーとボタンは消える。確認の状態（`S.pendingOrphan`）も、そのとき下ろす。
  - 「削除する」は、保存が競合して最新のファイルに当て直されると、確認を出したあとに増えた共有に無い枠も、まとめて消す（当て直しは編集 `removeOrphanSessions` を最新のデータに掛け直すため。確認の件数と食い違いうる。許容した）。
- 読み直し（「更新」・バナーの再読込）は、`reloadFile` だけが `store.reload()` を呼ぶ。読み直せなくても、`sync.reset()` で保存していない編集を捨て、再読込・書き出しのボタンつきのバナー「読み直せません: …（画面の内容は、まだファイルと違う可能性があります）」を出す。残る穴: 読み直せなかったとき、画面のデータ（`S.data`）には、捨てると伝えた編集が残り、次の保存で、外から変わっていない方のファイルには、そのまま書かれうる（読めないのでデータを差し替えられない）。
- 動作確認（Playwright、Chromium、`file://`、`?today=2026-10-20&time=10:15`）: `showOpenFilePicker` とファイルのハンドルを偽物に差し替え（中身は `splitData(data/sample.json)`、IndexedDB の記憶はハンドルの名前に置き換えて保存）、(a) 共有 → 個人の順に選ぶと画面が開く、(b) 共有だけのときは個人の案内とボタンだけが出る、(c) 再読み込みで 2 つとも自動で開き、権限が未確定（`prompt`）のときは「前回のファイル（data.json・personal.json）を開く」が出て、押すと開く、(d) 個人の記憶を消すと、共有だけが開いて個人の案内になる、(e) タスク名の変更は data.json だけを書く（個人の設定の変更が personal.json だけを書くことは、いまある項目では未確認）、(f) 共有ファイルを壊して「更新」すると、「読み直せません」のバナーが出る。共有に無い枠を足した個人ファイルで、バナーに注意の文とボタンが出る・スケジュールにその枠は出ない・ボタン → 確認 → 「やめる」で戻る・「削除する」で個人ファイルからその枠だけが消える（共有は変わらない）・共有にタスクを足して「更新」するとバナーが消える。`showOpenFilePicker` を消した状態では、2 つのファイルを入力欄で選ぶと画面が開き、「JSON を書き出す」が `data.json`・`personal.json` の 2 つをダウンロードした（中身のキーは分割後の形）。
- 未確認: 実際のファイル選択と権限の確認の画面（Edge・Chrome）、1 回の押下で 2 つの権限の確認が続けて出せるか、定期の読み直し（`pollInbox`）経由でのバナーの消え方、ネットワークドライブ・SharePoint 経由のファイル、保存の失敗中の個人ファイル側の再現、`showOpenFilePicker` の無い実ブラウザ（Firefox・Safari）での 2 つのダウンロード。

### ガントチャートとリスト

- ガントチャートは、土日・手動の休み（`settings.holidays`）・日本の祝日の列に、同じ着色（`.gwk`）を付ける。判定は `core/holidays.js` の `restDayChecker`。「土日祝を営業日に数える」の設定に関わらず着色する（日数の計算と作業枠にだけ効く設定のため）。営業日の指定（`workdays`）の日は着色しない。日表示（40 日以下の表示）のときだけ着色する（土日の着色と同じ）。
- 前のタスクの線は、編集画面のガントチャートだけに出す。`gantt.js` が、前のタスクのあるバーに `data-pre`（空白区切りの ID）を付け、`ui/deps.js` が、描画のあとにバーの位置を測って SVG（`.gdeps`）を重ねる。両端のバーが同じプロジェクトの表に出ているものだけ引く（「完了を隠す」で隠れた行・別のプロジェクトとの線は引かない）。バーのドラッグ中は、線がずれるので隠す。バーにマウスを置くと、`focusDeps` が、そのタスクを青、前のタスクを橙にし、つなぐ線を濃くし、ほかを薄くする。前のタスクも次のタスクもないバーは、自身だけを青にする（ほかは薄くしない）。
- ガントのラベルの ID の列は `56px`（`AA-0001` が等幅 11px で収まる幅）。幅 1400・900・600px で件名が詰まらないか、固定表示（`.gstrip`・`.thstrip`）がずれないかは、ブラウザで未確認。幅 640px 以下は、ラベルを 150px、ID の列を 40px（`--idw`）、ID の字を 9px にする（件名の列は、並べ替えの行で約 65px、ほかの行で約 80px と計算した。実測はしていない）。
- 開始日（`taskStart`）は、`start` があればそれ、なければ前のタスクの期限の最大値、それもなければ期限。前のタスクがあるタスクにも左端のつまみを出し、ドラッグすると `start` に保存する（前のタスクの期限は見ない）。`start` を指定したタスクは、前のタスクの期限が動いても動かない。リストの開始日を空にすると、指定を外す（前のタスクから決まる日に戻る）。前のタスクを足しても、開始日は触らない（画面は `addPredecessor`。外すと、利用者が入れた開始日が黙って消えるため。見送った案: 外したうえで通知する）。依頼で期限が指定した開始日より前になるときも、開始日を外して提案の注意に出す（外さないと保存の検査で失敗する）。前のタスクがあり `start` もあるデータは、`start` を使う。同梱のサンプルに該当はない（Excel 取り込みの結果は未確認）。
- 画面では、前後のタスクの確認をしない。期限・開始日の変更（リストの日付欄、ガントのドラッグ、編集の窓）は、そのタスクだけを保存する。次のタスクの期限を超えたときの警告、「前のタスクの期限より前にはできません」のエラー、日程変更の確認パネルは持たない。前後を見て動かすのは、「Claude Code に依頼する」の処理（`core/impact.js`）だけ。画面から期限を変えても、日程変更の履歴（`changeLog`）には残さない（履歴に残るのは、依頼の処理と取り込みの変更だけ）。
- バーにマウスを置くと（`focusDeps`）、そのタスクを青、前のタスクを橙、次のタスクを緑（`--next`）にし、前のタスクとの線を橙、次のタスクとの線を緑にする。ほかは薄くする。線の SVG は、前のタスクの ID を `data-from`、次のタスクの ID を `data-to` に持つ。
- 編集の窓（`views/taskpop.js`）は、ガントチャートでタスク名（`data-gedit`）またはバーをクリックすると開く。バーは、ドラッグせずに離したとき（`app.js` の mouseup で `dd` が 0）だけ開く。窓は `S.tpop`（`{ id, x, y }`、メモリのみ）で持ち、`fixed` で、クリックした位置の近くに置く（`placeTaskPop` が画面の端と下端の帯を避ける）。入力は、リストと同じ `data-f`・`data-id` を使うので、保存はリストの処理が受け持つ。状態の欄（待ち先・Done の確認を含む）と前のタスクの欄は、リストと共用（`statusCellHtml`・`predEditHtml`）。窓の外のクリック・Esc・タブの切り替え・ファイルの読み直しで閉じる。タスク名のクリックは窓を開く。リストへ移る動きは、窓の「リストで開く」にある。

- 「今日の優先」と「今日のタスク」の行には、チェックリストのあるタスクに細い線と「M/N（残り K 件）」を出す（今日のタスクの完了済み・取り消し済みの行には出さない）。

### 会議と稼働

- 予定表から取得した会議は、「参加しない」とプロジェクトだけ変更できる。
- 「参加しない」の会議（`skip: true`）は、スケジュール画面の右上の「参加しない会議」ボタンで、カレンダーに出す・隠すを切り替える。初めは隠す。隠すと、週・日の両方で描かず（選択中の会議だけは出す）、凡例の「参加しない会議」も出さない。稼働の計算とデータは、出す・隠すで変わらない（どちらでも、稼働に数えず、作業枠と重なっても注意しない）。状態は `S.prefs.showSkipped`（`prefs.js`）に持ち、`localStorage`（`project-lens.prefs`）に保存する。`data.json` には保存しない。
- 会議のプロジェクトは、規則（件名のキーワード → プロジェクト）で自動に付き（`projectBy` が `rule`）、手動で付けたもの（`manual`）は規則を変えても動かない。
- 稼働は、プロジェクト別のタスクの時間（実績の作業枠）と会議の時間（確認済みで、参加するもの）を集計する。プロジェクトのないタスク（`projectId: null`）の実績の作業枠と、プロジェクト未設定の会議は、「プロジェクト未設定」の行にまとめる（タスク列と会議列に分ける）。未確認の枠・会議は含まない。

### 設定タブ

- **節の構成と折りたたみ**: 節は 4 つ（基本の設定・休みと営業日・キーワード規則・WBS の取り込み記録）。「休みと営業日」の中に小見出しが 3 つ（日本の祝日・休み（手動）・営業日として扱う日）ある。7 つとも `<details>` で、見出しを押すと開閉する。

  - `app.js` が `toggle` イベントをキャプチャで受けて記録する（`toggle` はバブリングしない）。開閉では描き直さない。描き直したときは、`renderSettings` の `opts.closed` から開閉を復元する。

### 日本の祝日の取得

- `tools/holidays.js` の `update` が、内閣府の `syukujitsu.csv`（Shift_JIS）を取得して、前年以降だけを `nationalHolidays` に書く。失敗したら `data.json` を変えず終了コード 1。
- `status` は、取得日・件数・範囲・`ageDays` を出す。取得先は環境変数 `PROJECT_LENS_HOLIDAYS_URL` で変えられる。
- ブラウザからは CORS で取れないため、画面は取得しない。
- 更新の判定は `tools/holidays.js` の `needsHolidayUpdate(settings, neededUntil)`（未取得／取得から 30 日超／一覧の最終日が今日以前／`neededUntil` が一覧の最終日より後。今日取得したものは取り直さない。`settings.countWeekendsAndHolidays` が `true` のときは、常に取り直さない）。入口は 2 つ: `tools/holidays.js ensure`（`/project-lens:watch` を始めるとき。当てはまるときだけ取得し、失敗したら終了コード 1 で `data.json` を変えない）と、`tools/inbox.js propose`（`businessDays` を使う提案のとき、当てはまれば同じ取得を 1 回行って提案と一緒に保存する。取得できなかった・範囲を超えたままのときは、提案の `warnings` に書く。エージェントは祝日を確かめない）。手動で取るときは `tools/holidays.js update`（コマンド `/project-lens:holidays` はない）。
- 解析は `core/holidays.js` の純関数（`parseHolidayCsv`・`pickRecent`・`decodeHolidayCsv`）。

### 共有ファイルと個人ファイルの分割

データは、メモリ上では 1 つのまとまり（`S.data`）で、ファイルでは 2 つに分かれる。変換は `core/split.js` の純関数（`splitData`・`mergeData`）だけが行い、画面の各部・CLI の各コマンドは、結合した 1 つのデータのまま扱う。

| ファイル | 置くもの |
|---|---|
| 共有（`data.json`） | `projects`・`tasks`（作業枠 `sessions` を除く）・`changeLog`・`version`・未知のトップレベルのキー、設定のうち個人以外すべて（既知のものは `countWeekendsAndHolidays`・`nationalHolidays`・`waitingLongDays`・`projectRules`・`labels`・`wbsMappings`・`wbsImports`。未知のキーも共有） |
| 個人（`personal.json`） | `sessions`（`taskId` を持つ平らな配列）・`events`・`inbox`（あるときだけ）・`version`、設定のうち `holidays`・`workdays`・`selfEmails`・`selfNames`（`PERSONAL_SETTINGS`） |

- 個人ファイルの未知のトップレベルのキーは、結合で落ち、次に個人ファイルを書くときに消える（共有ファイルの未知のキーは残る）。結合したデータからは、どちらのファイルのキーだったか分からないため（残すには、個人のキーの一覧か印が要る。いまは個人ファイルに未知のキーを書く道具がないので、見送った）。
- 同梱のサンプルは `data/sample.json` 1 つで、分割前の結合した形（メモリ上の形）。`data/personal.json` のサンプルは無い。`init --sample` は、これを `splitData` して 2 つのファイルを書く。エージェントの指示がスキーマとして `sample.json` を指すのは、この結合した形のこと。サンプルとテストの ID は、採番する形にそろえる（プロジェクト `AA`〜`AC`、タスク `AA-0001`、プロジェクトなし `ZZ-0001`）。ID の形は検証しないが、例が実際の形を示すようにするため。ID の形を検証しないので、手で書いた別の形の ID（`A1`・`A` など）も受ける。採番（`nextProjectId`・`nextTaskId`）がそうした ID を無視することは、`edit.test.js` で確かめている。テストに出てくるほかの `A`・`A1` は ID ではない（プロジェクト名、大項目の名前、WBS の件名・前のタスクのキー、Excel の値・セル番地）。

- 結合（`mergeData`）は、個人の枠を `taskId` でタスクの `sessions` へ戻す。共有に無い `taskId` の枠は、`orphanSessions` に入れる（消さない。バナーの案内は「画面の動き > ファイルを開く」）。`splitData` は `orphanSessions` を個人の `sessions` へ戻すので、保存しても失われない。入力は変えない。
- 形の検査は `checkSharedShape`（`projects`・`tasks`・`changeLog` が配列）と `checkPersonalShape`（`sessions`・`events` が配列）。画面に渡す前に、2 つとも通す。`validate` は、共有に無いタスクの枠を注意（warning）にする。
- 旧形式（作業枠がタスクの中にある 1 ファイルの `data.json`）の移行・読み替えは持たない。旧形式のファイルは、手で直す。`checkSharedShape` は、タスクのどれかに `sessions` のキーがある、またはトップレベルに `events` があるとき、「作業枠・予定を含む 1 ファイルの旧形式の data.json です。personal.json へ手で分けてください」で例外にする（`isOldShared`）。読むと、個人ファイルが無い・空のとき、枠・予定が空のデータになり、次の保存（見張りの印の保存は `.bak` を作らない）で共有ファイルから消えるため。`splitData` は共有ファイルにどちらも書かないので、正しいファイルでは起きない。CLI の `readData`（`validate.js` を含む）・画面の `createPairStore`・`dataFromTexts` が、この検査で止める。`init` も、既存の `data.json` が旧形式なら、空の個人ファイルを隣に足さず、何も変えずに止める（読めない・形の違うファイルは、これまでどおり変えない）。
- 設計判断（なぜ分けたか）: 複数人でスケジュールを管理するとき、タスクは全員で共有し、作業枠・会議・休み・自分の特定・依頼は各自のものだから。
  - 見送った案（作業枠をタスクの中に残す）: 全員の作業枠が共有ファイルに入り、1 人の枠の編集のたびに共有ファイルが更新され、競合の当て直しが増える。他の人の予定も共有ファイルから見える（この理由は、分割の目的からの推測。試していない）。
  - 見送った案（https の URL での直接の読み書き。Microsoft Graph など）: 利用者の判断。ネットワークドライブ・同期フォルダ経由の共有ファイルで足りるため。
  - 見送った案（他の人の稼働・個人ファイルの表示、タスクの担当者の項目）: 利用者の判断。必要になってから足す。読むのは自分の個人ファイルだけ。
  - 見送った案（2 つのファイルをまとめて書く・競合を確かめる仕組み）: 利用者の判断。ファイルごとに独立して保存し、片方だけ書けた場合は、下の「保存と競合」の規則で扱う。
  - 見送った案（共有ファイルだけで開く動き）: 利用者の判断。個人ファイルが無いときは、画面を開かない。

### 保存と競合

保存と競合の検知・当て直し・自動の読み直しは、ファイルごとに独立している（ファイルごとに読み込み時点の印を持つ）。ロックは作らない。

#### CLI（`tools/cli.js`）

- 1 ファイルの保存（`save`）は、`readJson` で読んだ時点のファイルの印（更新日時とサイズ）を覚え、書く直前に比べる。違えば「他で更新されました」で止まる（もう一度読み直して実行する）。見張りの印を書く `wait` は、止まったら次の回に書く。`readJson` は、先頭の BOM（メモ帳などが付ける）を除く（画面は `file.text()` が除くので、そろえる）。置き換えが 3 回失敗したときは、上書きせず例外にする。
- 2 ファイルの読み書きは `readData`・`saveData`。共有ファイル（`data.json`）と個人ファイル（既定は同じフォルダの `personal.json`、`--mine <ファイル>` で別の場所。相対パスはいまのフォルダから）を、結合して扱う。`inbox.js`・`intake.js`・`holidays.js`・`validate.js` が使い、`init.js` は 2 ファイルを直接書く。`doctor.js` は保存先のフォルダだけを見るので変えない。
  - `--mine` に値が無い（末尾・空）ときは、既定の場所へ黙って戻さず、`--mine にファイルを指定してください` で終了コード 2（`takeMine` が例外、各ツールの入口 `takeMineOrExit` が終了コードにする）。
  - 既定の個人ファイルが無い（`ENOENT`）ときだけ、空の個人として読む。`--mine` で明示したファイルが無いときは、指定の誤りなので、空として読まず「個人ファイル … がありません。--mine の指定を確かめてください」で例外にする（`saveData` も、共有を書く前に同じ例外）。共有ファイルが無い・形が違うときも例外。
  - 読んだとき個人ファイルが無かった場合は、その印を覚え、保存の確認と書く直前に、他が作っていないかを見る。作られていたら、空の個人で上書きせず「他で更新されました」で止める。読んだあとに消されたファイルも、同じ文言で止める。
  - `saveData` は、結合したデータを `validate` に 1 回だけ通し、エラーなら何も書かない。通ったら分けて、中身が変わった方だけ書く（共有だけの変更で、個人ファイルの更新日時を動かさない）。
  - 書く前に、両方のファイルの競合を確かめる（片方を書いてから、もう片方の競合に気づく形にしないため）。書く順は、共有 → 個人。2 つ目の置き換えが失敗したときは、1 つ目を巻き戻さず、例外の文言に、書けたファイルと書けなかったファイルを書く（巻き戻しも別の書き込みで、失敗しうるため見送った）。たとえば `inbox approve` で、共有（タスクの変更）は書けて個人（依頼の状態）が書けないと、依頼は `proposed` のまま残る。もう一度 `approve` すると、提案の時点からタスクが変わっているので、古い提案（`stale`）として止まり、依頼は失敗の状態になりうる（未確認）。
  - `init.js` は、`saveData` を通さない（`--mine` で指す個人ファイルは、作る前で、まだ無いから）。既存のファイルは変えない。共有だけがあるときは、空の個人ファイルを作る（サンプルの個人データは、既存の共有と合わないので足さない）。共有を新しく作る `--sample` の隣に個人ファイルが既にあるときは、個人ファイルは変えず、「変えていません。サンプルの作業枠・予定は入っていません」と 1 行出す。`--sample` は、分割前の形の `data/sample.json` を `splitData` して書く。`.gitignore` に足すのは `.project-lens/` だけなので、`--mine` で `.project-lens/` の外を指した個人ファイルは、除外されない（利用者が自分で除外する）。
- 控え（`.bak`）: 検証と競合の確認に通ったあとに、直前の版を `<ファイル>.bak.tmp` へコピーしておき、置き換えに成功したあとで `<ファイル>.bak` にする（置き換えに失敗したときは、`.bak.tmp` を消し、1 つ前の `.bak` を残す。先に `.bak` を上書きすると、置き換えの失敗で 1 つ前の版を失うため）。書いたファイルごとに 1 世代（`data.json.bak`・`personal.json.bak`）。誤承認・誤った WBS の取り込み・予定表の誤削除を、戻せるようにするため。`.project-lens/` は git の対象外（`init` が `.gitignore` に追記する）で、`.bak` も同じフォルダなので同じ除外に入る。
  - 1 世代だけで、上書きする。元のファイルが無い（初回）ときは作らない。`.bak` が書けなくても、標準エラーに 1 行（`<パス>.bak を更新できませんでした: <理由>`）を出して、本体の保存は続ける（控えは補助で、止めると本体より副の機能が優先になるため。出さないと、古い `.bak` が新しい控えに見える）。検証に通らず例外のときは作らない。見張りの印だけの保存（`tools/inbox.js` の `wait`）は `{ backup: false }`（30 秒ごとに `.bak` を上書きすると、意味のある直前の版が消えるため）。
  - 効く範囲: `.bak` を作るのは CLI の保存だけ。画面の承認・編集は作らない。見張り中は、依頼のやりとり（claim・ask・propose など）や 30 分ごとの `calendar-auto` の保存で、すぐ上書きされるので、戻せるのは直後だけ。戻す前に `.bak` の更新日時を確かめる。画面での編集は `.bak` に入らないので、戻すとその分も失う（利用ガイドに同じ注意を書いている）。
  - 見送った案: 世代管理（日時付きの複数の控え。戻す場面は「直前の誤操作」で、1 世代で足り、ファイルの掃除の規則が要るため）。画面（`store.js`）側の `.bak`（画面は `showOpenFilePicker` で得たファイルのハンドルに `createWritable` で書く方式で、フォルダのハンドルを持たない。同じフォルダへ別ファイルを書くには別の権限が要ると考えられるが、実ブラウザでは未確認。画面での編集の誤りは、CLI 側の `.bak` ではなく、画面の「JSON を書き出す」で退避する）。

#### 画面（`ui/store.js` の `createStore`・`createPairStore`、`ui/sync.js`）

- `createPairStore` は、共有（IndexedDB のキー `dataFileHandle`、`checkSharedShape`）と個人（キー `personalFileHandle`、`checkPersonalShape`）の 2 つの `createStore` を持ち、結合した 1 つのデータ（`mergeData` の形）で受け渡す。画面は `createPairStore()` を使う。
- 開く: `choose(which)`（`"shared"` か `"personal"`）・`restore`・`reopen` は、2 つとも開いたときだけ結合したデータを返し、そうでなければ `null`。まだ開いていない方は `missing()`、記憶した名前は `lastFile()`（`{ shared, personal }`）。`hasFile` は 2 つとも開いているときだけ真。`reopen` は、開いていない方のうち記憶のある方だけ、権限の確認を続けて出す（記憶の無い方は開かず、`missing()` に残す。開こうとすると「書き込みが許可されませんでした」という誤った文言になるため）。
- 開く・読み直すときは、`createStore` が、画面に渡す前にデータの形を検査する（共有は `checkSharedShape`、個人は `checkPersonalShape`）。別のファイルを開く・前回のファイルを開く・自動オープンは、読めて形が合ったときだけ、保存先と記憶を切り替える（`switchTo`）。先に切り替えると、形が違って開けなかったファイルへ、画面に残った前のデータを保存し、そのファイルを丸ごと上書きするため。形が違うときの読み直し（「更新」・自動）は、画面のデータを差し替えずに、例外（自動のときは次の回に再試行）にする。形は合うが `validate` に通らないデータは、バナーを出して開く。JSON として読めないファイルは「JSON として読めません（<ファイル名>）」で開かない（`createStore` と `dataFromTexts`。`dataFromTexts` は、画面が渡すファイル名を使う）。
- `peek`・`reload` は、2 つのファイルの最新を `mergeData` した形を返す（`ui/sync.js` が `peek` を `getData()` と `JSON.stringify` で比べるので、`orphanSessions` を含めて同じ形にそろえる）。
- 保存（`save`・`saveMerged`）は、`splitData` で分けた 2 つのうち、直前に読んだ（保存した）内容から変わった方だけを、共有 → 個人の順に、それぞれの `createStore` で書く。比べるのは、直前の内容を `splitData(mergeData(…))` した形（ファイルのキーの順の違いで、変わっていない方を書かないように）。書く前に、ファイルごとに、更新日時を比べ、他（Claude Code など）が更新していたら上書きせず conflict を返す。
- 当て直し（`saveMerged` の競合）は、「そのファイルの最新」と「もう片方の、編集を当てる前の内容」を `mergeData` し、`edit` を当て、`splitData` で取り出したそのファイルの分を書く。当て直したときは、結合した最新を `data` で返す（当て直していなければ、渡したデータそのもの）。画面のデータは `mergeData` の形になり、`peek` との比べでキーの順などが違えば、1 回余分に読み直す（害はない）。当て直せなかったとき（同じ依頼がすでに処理されていた、など）だけ、保存時に「他で更新されました。再読込してください」と出て、上書きしない。読み直すと、画面の保存できていない変更は消える。
- 当て直しの保存が失敗したとき（書き込みの権限・I/O のエラー）は、読み込み時点（`loadedAt`）を元に戻す。進めたままだと、次の保存が競合を検出せず、画面の古いデータで他の更新を上書きする。
- 片方だけ成功したとき: 結果は `{ ok: false, reason, message: "<data.json か personal.json>: …", data }`。書けた方は、その内容と `loadedAt` を進め（次の保存で競合にしない）、失敗した方は直前の内容のままなので、次の保存で書き直す。巻き戻しはしない（CLI と同じ理由）。ファイル名は、実際のファイル名でなく、`data.json`・`personal.json` で出す（`--mine` で別名の個人ファイルを選んでも同じ）。
- 片方だけ成功したとき、書けた方を当て直さずに書けていたら、そのファイルの「編集を当てる前の内容」を覚える（`prior`）。`sync.js` は、失敗した保存の編集を持ったまま次の保存で当て直すので、失敗した方の当て直しの土台は、書けた内容ではなく、これにする（書けた内容を土台にすると、同じ編集を 2 回当てる。ID を編集の中で決めるタスクの追加なら、共有のタスクと個人の枠の ID がずれる）。書けた方自身も、次の保存では `saveMerged` でなく `save` で書く（その間に外から変わっていたら conflict）。`edit` の無い `save` は、そのまま書ける。すべて成功する・読み直す・開き直すと消える。
- 画面のデータが、片方のファイルより古くなったとき（書けた方を当て直していて、もう片方が失敗した）は、そのファイルの、編集を当てる前の内容を覚える（`behind`）。次の保存では、画面のデータではなく、その土台に `edit` を当て直したものを、`saveMerged` でなく `save` で書く（画面の古いデータで、他の更新を上書きしないため）。その間にそのファイルが外からさらに変わっていたら、2 回目の当て直しはせず conflict（すでに書いた編集を 2 回当てないため。利用者が再読込する）。`edit` の無い `save` も conflict。読み直し・開き直しが両方とも通ると消える。
- `reload` は、2 つとも読めて形が合ってから、両方の読み込み時点を進める（子の `read` で読み、`commit` で進める）。片方でも読めない・形が違うときは、何も変えずに例外（何も読み直さない）。片方だけ進めると、画面の古いデータが、その方の他の更新を競合なしで上書きするため。何も変えなければ、次の保存は競合になり、ふだんの当て直しで追いつく（読み直した内容を土台にする案は、`sync.js` がまだ持つ、書けた編集を 2 回当てるので見送った）。
- 保存と読み直しの順序づけは `ui/sync.js`（`createSync`）。画面の編集を 1 本の列に並べて保存し、競合したら最新のファイルに同じ編集を当て直す。Claude Code の更新の読み直し（`pollInbox`）も同じ列に並べる。画面は、ファイルを自動で読み直す（保存できる環境のとき）。帯が開いている間や依頼の処理中は 4 秒、そうでなければ 16 秒ごと。
- 打ちかけの入力の間は、読み直しの描き直しを待たせる: `createSync` の `isEditing`（`app.js` の `isEditing`）は、`#view` の中のフォーカスのある入力欄（`input` の文字・日付・時刻などと `textarea`。チェックボックス・選択欄は除く）の `value` が `defaultValue`（描いたときの値）と違うときに真。真の間、`pollInbox` は `setData` でデータだけ取り込み、`render` を `sync.flush()` まで待たせる。`app.js` は、`#view` の `change`（その欄の `onChange` のあと）と `focusout`（フォーカスが移り終わったあと）で `flush` を呼ぶ。`flush` は、まだ打ちかけなら何もしない。ほかの理由の `render` は、待たせた描き直しを捨てる（`sync.rendered()`）。ファイルを開き直す（`sync.reset()`）ときも捨てる。打ちかけでなければ、すぐ描き直す。受信箱だけの変化（`renderBar`）は `#view` を描き直さないので、待たせない。
  - 確定で下書き・データに写さない欄（チェックリストの追加欄 `data-ckadd`、待ち先の入力 `data-waitparty` など）は、フォーカスが離れたあとの描き直しで、打った文字が消える（直していない）。保存の当て直し（`persist`）の描き直しは、待たせない。会議の入力欄など、コードが値を入れ直した欄（`endInput.value = end` など）は、`value` が `defaultValue` と違ったままになるので、フォーカスが離れるまで描き直しを待たせる。
  - マウスのボタンを押している間（`pointerdown` から `pointerup`・`pointercancel` まで。3 秒で打ち切る）は、`flush` をしない。押した瞬間の `change`・`focusout` で描き直すと、押したボタンが作り直され、離したときのクリックが届かない（1 回目のクリックが効かない）ため。離したあと（`click` の処理のあと）に `flush` する。キーボードでの移動（Tab）は、すぐ `flush` する。
  - 動作確認（Chromium・Playwright、`?today=2026-10-20&time=10:15`、`showOpenFilePicker` を偽のファイルに差し替えて `splitData(sample.json)` を読み込んだ）: 突発タスクの件名を打ちかけのまま、外から共有ファイルのタスク名を変えて 17.5 秒待つと、件名は残り、画面はまだ古い。フォーカスを外す・Tab で次の欄へ移ると、新しいタスク名が出て、件名も残り、フォーカスは次の欄にある。打ちかけでないときは、読み直しですぐ新しいタスク名が出る。未確認: 実際の日本語入力（IME）の変換中、ほかの入力欄（編集の窓・スケジュールの編集欄・会議・リスト・チェックリスト）。
- 直接保存に対応しないブラウザでは、「JSON を書き出す」が 2 つのファイルをダウンロードする。読み込みは、2 つのファイルを一度に選ぶ（「画面の動き > ファイルを開く」）。

#### 見送ったこと・未確認

- 見送ったこと（既知の穴）: 保存の確認と書き込みの間の競合。CLI も画面（`store.js` の `save`）も、「更新日時を見る → 書く」の 2 段階で、プロセスをまたぐロックはない。確認と書き込みの間（数ミリ秒）に相手が書くと、その編集は検出されず消える。起きうる組み合わせは、見張り（`wait`）の見ている印（30 秒ごとに個人ファイルを書き直す。共有ファイルは書かない）と、画面での個人ファイルの編集が、同じ数ミリ秒に重なるとき。消えるのは直前の 1 回の編集で、画面なら再読み込みの後に気づく。ロックファイルは、小さな規模には過剰なので入れない。1 つの共有ファイルを複数人が使うと、共有ファイルでは、人どうしの編集が同じ数ミリ秒に重なる組み合わせも加わる。確認していないこと: 実際に編集が消えるかを、2 つのプロセスで同時に書いて試していない（未確認）。
- 実ブラウザで未確認: 2 つのファイルの権限の確認、自動の読み直し（`pollInbox`）と組み合わせた動き、SharePoint・ネットワークドライブ上のファイルでの更新日時の扱いと自動の読み直しの遅さ。
- 枠の長さを変える操作（`resizeSession`）も、移動・追加と同じく、会議と重なるときは `warning` を返す。画面は、操作の結果の文に添える。
- 前回のファイルの記憶は、Edge で `file://` から開いて効くことを確認した。権限の確認の文言は Edge のバージョンで違う想定で、実際の文言と「何も押さずに開く」動きは未確認。

## 取り込み（intake）

WBS と規則は「読み取り → 変更案の表 → 利用者の承認 → 書き込み」の順で、承認の前はタスクを変えない。予定表の会議は、承認の確認なしで書く（後述）。

- **タスクの登録（文章での依頼）**: `intake` ではなく、HTML の依頼で行う（`inbox` エージェントが、依頼の文章から `addTask`・`moveDue` の提案を作る）。メール・議事録・メモの本文の取り込みは、目的の外（受けない）。次の 2 項目は、その手順の規則。
  - 期限が書かれていないタスクは、Claude が前のタスクと `businessDays` で仮に置き、日付の足し算は `propose` が行う。行番号で直して再提案し、承認後に登録する。
  - 重要・待ち先（状態）は、依頼では受けないので入れない（画面で設定する）。
- **WBS**: 列の対応と変更案を一緒に見せて承認を 1 回にする（承認後に `mapping-set` → `wbs-apply`）。
  - 質問・承認・入れ先の選択は、`/project-lens:intake` を実行している会話が受け持つ。`intake` エージェントは、質問（プロジェクト・シート、`rules` で案がないときの規則）、`xlsx.js setup` の表示と 2 つの依頼の行（`（setup 承認済み venv）`・`（setup 承認済み system）`）、変更案と承認の依頼（`（承認済み <planKey> "<rows.json>" "<mapping.json>"）`）を報告して終わる。会話が利用者に聞き、選ばれた行・承認の依頼を、新しいエージェントにそのまま頼む。保存済みの列の対応を使う再取り込みでも、エージェントはその内容を一時フォルダの `mapping.json` に書き、承認の依頼にパスを入れる（新しいエージェントは、渡されたファイルだけで書くため）。承認の依頼を受けたエージェントは、手順 1〜5 をやり直さず、渡されたファイルで書く。規則（`rules`）も同じで、承認の依頼は `rules（承認済み）<案の一覧>`。
  - `wbs-plan` は、変更案（追加と更新）の指紋 `planKey` を出す。`wbs-apply --plan-key <planKey>` は、書く時点の変更案の指紋が違えば、何も書かずに終了コード 1 で止まる（承認を待つ間に、画面での編集や `rows.json` の変更があると、承認していない内容で書くため）。`--plan-key` を省くと照合しないが、エージェント（`intake`）は必ず渡す。`--plan-key` を付けて値が無いときは、照合を黙って省かず、終了コード 2 で止まる。
  - 「WBS に無い既存タスク」（`missing`）は、WBS に書かれていないキーだけ。形が不正で弾いた行のキーは、WBS に書かれているので、含めない（日付の打ち間違い 1 行で、実在のタスクが消えたことになるため）。
  - 開始日が期限より後の行は、前のタスクの解決の前に弾く（あとで弾くと、その行を前のタスクにした行が、警告なしに前のタスクを失う）。
  - 循環の判定のノードは、取り込み先のプロジェクトのタスクだけ `wbsKey`、ほかのプロジェクトのタスクは ID にする（`wbsKey` はプロジェクトをまたいで一意でなく、同じ雛形の WBS は同じキーを持つため）。前のタスクを指定した行は、最終形に置き換わるので、先に全部空にしてから判定する（行の順序で結果を変えない）。
  - 前のタスクの循環は、`wbs-plan` で検出する。既存のタスクの関係を含めて、循環になる指定だけを設定せず、警告に出す（ほかの行は取り込む）。`wbs-apply` で全体が例外になると、仮の ID しか出ず、原因の行が分からないため。ガントチャート・リストの変更履歴は、`source` があり日数が 0 の記録を出さない。
- **予定表**: 取り込みの結果に、使った MCP 名を出す。`/project-lens:intake calendar` は、変更案の表も承認の確認もなしで、`calendar-auto` を実行して書く（見張りからの呼び出しと同じ手順）。確認済みの実績を承認なしで消さないため。
  - 承認を外した理由: 承認なしで `calendar-apply`（`syncMcpEvents`）を使うと、予定表から消えた・対象外になった確認済みの会議（実績）が消える。実績を残す動きは `calendar-auto` にあるので、そちらに揃えた。
  - 自分だけ・自分と会議室だけの予定は、取り込まない（`import/calendar.js` の `excludeSolo`。純関数で、`planCalendarSync` が `syncMcpEvents` の前に呼ぶ）。取得した予定の `attendees`（`[{type: "person"|"resource", email, name}]`）から判定する。
    - 自分 = `email` が `selfEmails` のどれかと一致、または `name` が `selfNames` のどれかと一致（どちらも、前後の空白と大文字小文字を区別しない完全一致）。会議室 = `type` が `resource`、または `name` が `roomKeywords`（既定は「会議室」）を含む。自分と会議室を除いた参加者が 0 人なら対象外。
    - `attendees` の項目がない予定は、参加者が不明なので、取り込む。空の配列は「参加者なし」として対象外にする。MCP が参加者を返さないときに、エージェントが空の配列を書かないよう、`plugins/project-lens/skills/intake/SKILL.md` と `plugins/project-lens/skills/watch/SKILL.md` の両方の本文に書いてある（`fetched.json` を書くのは、どちらも呼び出し元の会話のため）。日付・時刻の書式（`YYYY-MM-DD`・`HH:MM`）も同じ。2 か所の食い違いは、`tests/agents.test.js` で調べる。
    - `attendees` の要素が `null`・文字列など、形が崩れている予定も、不明として取り込む（例外にしない）。
    - `selfEmails` も `selfNames` も未設定なら、自分を特定できないので、何も除かない（参加者つきの予定があれば `warnings` に出す）。どちらかを設定済みでも、どの予定にも `attendees` がないときは、判定できていないと `warnings` に出す（MCP が参加者を返さないと、機能が黙って効かなくなるため）。
    - 設定は `project-lens-mcp.json` の `calendar` の任意の項目 `selfEmails`・`selfNames`・`roomKeywords`（空でない文字列の配列）。`tools/intake.js calendar-plan|calendar-apply|calendar-auto` が、置き場（`PROJECT_LENS_HOME` か `--data`）から読む。判定を LLM に任せず、CLI で行うため。`schema_version` は上げない（任意の項目の追加。既存のファイルはそのまま読める）。
    - `/project-lens:mcp` は、引数が `show` のときだけ表示で終わる。引数なしでも、指定の手順へ進む。予定表の指定がすでにあるときは、変えるかを聞き、変えないなら手順4 へ進む。
    - `/project-lens:mcp` は、`selfEmails` か `selfNames` が保存済みなら、手順4 で聞かずに保存済みの値を伝える（変えたいと言われたときだけ聞き直す）。名前は完全一致なので、手順5 の試し取得で、取れた参加者の表示名を見せ、保存した名前と同じものがあるかを利用者に確かめてもらう（一致しないと警告なしで除外されないため）。同じものがない・確かめられないときは、手順4 に戻って入れ直すかを聞く。`selfEmails` だけが保存済みの人には、保存済みの値を伝えるときに「名前も保存できる」と一言添える（聞くかどうかの条件は「どちらかが保存済みなら聞かない」のまま。両方が保存済みのときだけ聞かない形にすると、名前を使わない人に毎回聞くことになるため）。同じ表示名の別人がいると、その人を自分とみなすため、心当たりがないかも確かめる。カンマを含む表示名（「Yamada, Taro」など）は、保存の区切りと同じなので、保存できない（メールアドレスだけにする。エスケープには対応しない。名前にカンマがある人は少ないと見て、見送った）。入れ直すときは、手順4 の「保存済みなら、聞かずに」にかかわらず、名前を聞き直す。
    - `/project-lens:mcp` は、保存のコマンド（手順4）に、答えのあった項目だけを渡す。答えのなかった項目を空（`selfEmails=` など）で渡すと、保存済みの値が消える（`setMcpRole` は、書かれなかった項目を残し、空の項目を消す）ため。消したいときだけ、空で渡す。
    - `mcpconf.js set` は、保存済みの値に合成する（`set calendar selfEmails=…` だけで足せる）。不明な項目（打ち間違い）は例外にする（黙って無視すると、除外されないことに気づけないため）。
    - 取り込み済みの会議が対象外になると、次の取り込みで `removed`（削除）に出る。終わった会議と `confirmed: true`（稼働の実績に数えている）のものは、`calendar-auto` が残す（`held`）。`calendar-plan` の出力は `{added, updated, removed, excluded, removedByExclusion, warnings, planKey}`（`removedByExclusion` は、対象外になって消える取り込み済みの会議 `{id, title, date, confirmed}`。確認済みの実績が消えることを、エージェントの文章に頼らず、出力で見せるため。`excluded` は `{externalId, title, date, start, end}` だけ。参加者のメールアドレスを、エージェントの文脈に出さないため）、`calendar-apply` の `summary` に `excluded`（件数）が付く（`held` はない。`calendar-apply` は終わった会議・確認済みの会議も消すため）。`calendar-apply` は `--plan-key <planKey>` を必須にする。`planKey` は、`calendar-plan` の `removed` の ID の並び（昇順）の指紋で、いま計算した値と違うときは、何も書かずに終了コード 1 で止まる。利用者が一覧を見て「はい」と答えたあとで、取得し直した結果が欠けて消える会議が増えても、確認していない削除をしないため（`wbs-apply` の `--plan-key` と同じ仕組み。ただし `wbs-apply` は省略できるが、こちらは省略できない。省略を許すと、この照合を黙って省けるため）。設定ファイル（`project-lens-mcp.json`）の指定が正しくない（`selfEmails` が文字列、など）ときは、`validateMcpConfig` の理由を出して止まる。エージェントは、取り込みの後に、参加者のメールアドレスを含む `fetched.json` を消す。
    - 名前のキーワード（`roomKeywords`）は、`type` に関係なく、人の名前にも部分一致する（`resource` 種別を返さない MCP でも、会議室を判定できるように、承認済みの仕様とした）。キーワードに短い言葉を足すと、人の名前に当たって、本物の会議を除外しうる。除外は、新しい予定では件数にしか出ない。取り込み済みの会議が除外されたときだけ、削除の行に件名が出る（`calendar-auto` では、終わった会議・確認済みの会議は残る。消えるのは、これからの未確認の会議）。
    - 見送った案: 辞退した予定の除外、手入力の会議の除外、定期的な予定のシリーズ単位の判定。
  - **自動更新（`calendar`。見張りからの依頼は `calendar <開始日> <終了日> "<パス>" <MCP名>（見張りから）`）**: `/project-lens:watch` が、見張りの開始時と 30 分ごとの再起動時に、会話で予定表を取得して `fetched.json` に書き、`project-lens:intake-calendar` エージェントへ渡す（手順1.5。Monitor を起動した後に行う。MCP ツールの許可確認が出ても、依頼の見張りの開始が止まらないように。取り込みの段階はバックグラウンドで行う）。承認の確認なしで `tools/intake.js calendar-auto` を実行して書く。見張り中は端末で止まれないため。
    - 取り込みの段階のエージェントは**バックグラウンドで**頼む（前景で呼ぶと、更新の間、見張りの依頼の処理が止まるため）。限界（受け入れた）: 取得は会話本体の前景で行うので、許可の確認や MCP の遅延の間は、依頼の処理も止まる。エージェントの報告は、`blocked`・`warnings`・`held` を含めて、そのまま利用者に伝える（サブエージェントの報告は、利用者の画面に出ないため）。`blocked` の理由には、次の行動（`/project-lens:mcp`、`/project-lens:intake calendar`）を書く。全件が対象外のときの停止は、休暇などで 14 日分が本当に空になった場合も止める。手動の `calendar` で `blocked` のとき、エージェントは削除せず、`calendar-plan` で消える会議（件名・日付）と `planKey` を示して終わる（エージェントは質問して待てないため、エージェントの中では確認が成立しない。このときだけ `fetched.json` を消さず、呼び出し元の会話が持ち、利用者の答えのあとに消す）。削除は、呼び出し元の会話が、一覧を見せて削除してよいかを利用者に聞き（終わった会議・確認済みの会議も消えると添える）、「はい」のときだけ、取得し直して新しい `fetched.json` を書き、依頼の末尾に `（削除確認済み <planKey>）` を付けてエージェントに頼む（エージェントが `calendar-apply --plan-key <planKey>` を実行する）。見張りからのときは聞かない（`（見張りから）` が付く依頼は、`（削除確認済み …）` が付いていても無視して `calendar-auto` を実行する）。`fetched.json` は、`node "${CLAUDE_PLUGIN_ROOT}/tools/intake.js" fetched-remove "<パス>"` で消す（Git Bash と PowerShell のどちらでも動く。`rm` や `Remove-Item` はシェルで書き方が違うため使わない）。`fetched-remove` は、ファイル名が `project-lens-fetched-*.json` で、かつ一時フォルダ（`os.tmpdir()`）の下（深さは問わない。`realpath` で正規化して比べる。`..` やシンボリックリンクで外へ出る形は拒否）にあるときだけ消す。合わないときは、何も消さず、理由を出して終了コード 1。ファイルが無ければ、成功で何もしない。`/project-lens:watch` の `allowed-tools` には、この `fetched-remove` だけを事前許可している。見送った案: `node -e` で `rmSync` を実行する許可。コードは固定でも、パスが任意なので、見張り中（外の人が書く件名を読む会話）に、任意のファイルを強制削除できる許可になるため（パスが任意の許可は置かない）。
    - 純関数 `planAutoSync`（`import/calendar.js`）が、`planCalendarSync` の結果から、終わった会議（`meetingPast`）と確認済みの会議の、更新と削除を取り除く（`held` に出す）。実績になる記録を、予定表での変更や取得の不具合で失わないため。予定表から消えた会議は、終わっていなければ（進行中・これから）削除する。ただし「参加しない」の会議は、取得に無いだけなら残す（利用者の印を、取得の欠けや externalId の変化で失わないため）。取り込みの対象外（自分だけの予定）になった会議は、「参加しない」でも消す。
    - 取得が 0 件、または全件が対象外になって、削除の対象があるときは、削除しない（`blocked` に理由を出す）。MCP が取得に失敗して空を返しても、自分のメールアドレスの設定が誤っていても、会議を全部消さないため。取得の失敗（ツールが使えない・エラー・結果が切り詰められた）は、会話が `fetched.json` を書かず、エージェントを呼ばずに、1 行で知らせる。`fetched.json`（メールアドレスを含む）は、成功しても失敗しても消す。
    - 取得が一部しか返らなかったかもしれないときも、削除しない（`blocked`）。条件は、削除する未確認の会議が 3 件以上（`PARTIAL_MIN`）で、かつ、取得の範囲内の取り込み済みの会議（終わった・確認済み・「参加しない」を除く）の半数を超えること。ページングや件数の上限で取得が欠けても、エージェントが写し落としても、未来の会議と手動のひも付けを、承認なしで失わないため。見張りの間は止まったまま終わり、手動の `calendar` は、消える会議を示して終わり、会話が聞く。見送った案: 取得が取り込み済みより減ったら、いつも止める（会議が 1 件キャンセルされるたびに確認が出て、承認なしで更新する意味がなくなる）。閾値は仮の値で、実データで調整する余地がある（未確認）。
    - 取得した予定は、`planCalendarSync` の先頭で検査する。`externalId` が空でない文字列、`title` が文字列、日付が `YYYY-MM-DD`、開始・終了が `HH:MM` で終了が開始より後でなければ、取り込まず `warnings` に出す（終日の予定・24:00・秒つきの時刻など）。取り込まれない終日の予定の日は、カレンダーに会議が出ず、作業枠との重なりの注意も出ない。1 件でも不正だと、保存の検証が全体を断り、その応答が予定表に残る間、自動更新が毎回失敗するため。不正でも `externalId` が読めた予定は、取り込み済みの会議を取得に無い扱いで消さない。同じ `externalId` が重なる予定は、最初の 1 件だけを取り込み、`warnings` に出す。
    - 守っていないこと（受け入れた）: 取得が一部だけで、消える会議が 3 件未満、または取り込み済みの半数以下のときは、書かれなかった未確認の会議が削除される（欠けと本当のキャンセルを、コードでは区別できない）。MCP が日時のタイムゾーンをずらして返すと、未確認の会議の日時が、そのまま上書きされる。保存の競合は、既存の `save` と同じ（ロックなし。CLI は `readJson` で読んでから書くまでに他が書き換えていれば、書かずに例外にする。HTML は画面の競合の扱いに従う）。
    - 範囲は今日から 14 日後まで。範囲の外と手入力の会議は変わらない。「自分だけの予定を除く」設定も効く。
    - `calendar-auto` の出力は `{ok, summary: {added, updated, removed, excluded, held}, held, blocked, warnings}`。`held` は `{id, title, date, change: "updated"|"removed"}`。時刻は `nowLocal()`（実行時の現在）で判定する。
    - 見送った案: 終わった会議も、予定表から消えたら削除する（稼働の実績を失うため）。更新を見張りの開始時だけにする（見張りが長く続くと、予定表が古くなる）。HTML の「更新」ボタン。
    - 未確認: 実際の予定表 MCP での動作。見張りの開始時に、予定表の MCP ツールの許可確認が出て、止まるかは未確認（出た場合は、一度許可すれば、以降は止まらない想定）。実際の予定表 MCP での動作は未確認（参加者の返り方は MCP ごとに違う）。

### Excel の WBS

- 列の意味（大項目・中項目・件名・期限・前のタスクなど）は Claude が見出しと内容から判断し、対応表を見せて確認を取る。承認された対応表はプロジェクトごとに保存する（`settings.wbsMappings`）。
- 階層は、列・結合セル・インデント・番号のどれで表されていても読める。末尾の行（子を持たない行）をタスク（小項目）にし、その上の 2 段を大項目・中項目にする。
- 再取り込みでは、`wbsKey`（大項目/中項目/件名の連結）で同じタスクを探し、期限などを更新する。
  - `wbsKey` を持たない手入力のタスクは、同じ件名のものが 1 つだけなら同じタスクとして扱い、取り込みで `wbsKey` を付ける（重複して追加しない）。
  - 画面で直した件名は上書きしない。
  - WBS に無くなった既存のタスクは削除せず、一覧で知らせる。
- Python 3.12 以上と pip が要る。システムの Python に使える openpyxl があれば、何も入れずにそれを使う。無ければ、初回だけ、プラグイン専用のフォルダの `venv` を作り、その中に `openpyxl` と依存の `et_xmlfile`、`defusedxml` を入れる（`--system` なら、システムの Python のユーザー領域。ネットワークが必要。約 20 MB、約 10 秒）。承認なしには入れない。
- `tools/xlsx_dump.py` が読む範囲は、1 シートにつき 5000 行 × 200 列まで（出力は最大 2000 行。範囲がそれより広いシートは `truncated: true`）。遠い隅にセルが 1 つあるだけで範囲が `A1:XFD1048576` まで広がり、全部を読もうとして終わらなくなるため（`tests/fixtures/wbs-stray-cell.xlsx` で再現。修正前は 20 秒で打ち切るまで止まっていた）。
- 非表示の列の範囲（`<col min max hidden>`）も、読む範囲（200 列）で切る。`max="2000000000"` のような細工で、非表示の列の集合が 20 億件になり、終わらなくなるため（`tests/fixtures/wbs-hidden-cols-bomb.xlsx` で再現。修正前は 20 秒で打ち切るまで止まっていた）。
- `tools/xlsx_dump.py` は、展開後の合計サイズが 300MB を超える xlsx を、読む前に断る（openpyxl は範囲を絞る前にシート全体をメモリへ読むため）。`read_only` での読み込みは見送った: 結合セルの展開と非表示の行・列の判定に、通常モードの `merged_cells`・`row_dimensions` が要る。
- WBS の取り込み（`import/wbs.js`）は、開始日が期限より後になる行（行の値、または既存タスクの値との組み合わせ）を `rejected` に入れる。通すと、新規ではガントの行が逆になり、更新では `updateTask` が例外を投げて取り込み全体が止まるため。
- タスクの開始日が期限より後は、`validate` が errors にする（プロジェクトと同じ扱い）。画面の編集（`ui/edit.js`）、WBS の取り込み、依頼の `addTask` も、同じ条件を拒む。前のタスクの期限が自分の期限より後は、正当な場合があるので warning のまま。errors のデータは `tools/cli.js` の `save` が書き込みを拒むため、既存のデータに逆転があるときは、手で日付を直す。
- `tools/xlsx.js` のサブコマンド:
  - `doctor`: 診断のみ。何も変更せず、使う Python のパスと、openpyxl の場所（システムか専用の venv か）を表示する。
  - `setup`: `--yes` なしは入れ先（専用の venv・システム）と内容を表示して終了コード 3、`--yes` で入れる（既定は venv、`--system` を足すとシステムのユーザー領域）。知らない引数（旧 `--into` を含む）は、使い方を出して終了コード 2。
- `tools/xlsx.js` の終了コード: 0 成功、1 実行時のエラー、2 引数・設定のエラー（置き場が決まらないなど）、3 読み取りの環境が使えない（システムにも専用の venv にも無い・版のずれ・壊れている・承認待ち・Python が無い）。3 のときは、利用者に入れ先を確認して `setup --yes`（システムは `--system --yes`）を実行する。
- 置き場の優先順: 環境変数 `PROJECT_LENS_HOME` → 引数（`--data "${CLAUDE_PLUGIN_DATA}"`）→ なければ終了コード 2。`tools/mcpconf.js` も同じ。

## HTML からの依頼（inbox）

### 動き

- 処理待ち（`pending`）・処理中（`working`）の依頼にも、画面に「却下する」を出す。見張りが止まる、受け取った後にセッションが落ちるなどで、`wait` が知らせない依頼（`working`）は、誰も処理しない。画面から取り下げられるようにした。見送った案: `wait` が受け取って長く経った `working` を再通知する（`submit --working` の依頼と区別する材料が要る）。

- 画面の下端の帯「Claude Code に依頼する」から、日程の見直し（`moveDue`）・タスクの登録（`addTask`）を依頼する。依頼は `data.json` の `inbox` に書かれ、見張っている Claude Code が提案（変更案）を作る。承認するまで、タスクの日程・前のタスク・一覧は変わらない。
- 依頼で受ける操作は `addTask` と `moveDue` の 2 種類だけ（`core/schema.js` の `PROPOSE_OPS`）。状態・重要の変更、削除、プロジェクトの追加と変更、マイルストーン、チェックリストの項目の変更、前のタスクの付け外しは、画面で行う。`inbox` エージェントは、そのような依頼に、`ask` で「この依頼は画面で行ってください」と返し、提案を作らない。
- できないこと: 会議の追加・削除。Excel の WBS・予定表・会議の規則の取り込みは `/project-lens:intake`。
- プロジェクトなしのタスクは、依頼の `addTask`（プロジェクトの指定が必須）・`moveDue`・WBS の取り込みの対象外。`moveDue` の影響の計算に、プロジェクトなしのタスクがあっても落ちず、前のタスクのないプロジェクトなしのタスクは、依頼の対象を絞る処理に含まれず、動かさない（直接 `moveDue` で指したときは、動く。単体テスト `tests/inboxops.test.js` で、対象の行に含まれず、期限が変わらず、検証の error が 0 件なことを確かめた。直接指したときの動きは、`planOps` で ZZ-0001 が +3 日になることだけ確かめた）。画面は、プロジェクトなしのタスクに前のタスクを付けさせない（`predecessorCandidates` が空を返す）ので、通常は連鎖で動かされない。ただし、影響の計算（`computeImpact`・`planOps`）はプロジェクトを見ないので、`data.json` を手で直して、プロジェクトなしのタスクに前のタスクを付けると、その前のタスクの遅れで連鎖して動く（サンプルの写しに、AA-0003 を前のタスクにするプロジェクトなしのタスクを足し、`planOps` で AA-0003 を +30 日にすると、そのタスクも同じ日に動き、`validate` の error は 0 件なことを確かめた）。実ブラウザ・実際の依頼の処理は未確認。
- 履歴は最新の 20 件まで（処理中のものは消えない）。1 件の文章は 4000 文字まで（やりとりの件数の上限は無い。「設計判断」を参照）。
- 変更履歴には、期限を動かす操作ごとに 1 件（日数・理由つき）と、登録があるときの 1 件（`source` が `inbox`。画面の「日程変更の履歴」には出ない）が残る。登録の 1 件の `reason` は「受信箱: 登録 N 件・期限の変更 N 件」の形（要約も同じ形）。

### 反映の規則

- 操作は、`addTask`→`moveDue` の順に当てる（それぞれ書かれた順）。`addTask` の前のタスクは、全部足してから結ぶ。前のタスクを足したとき、次のタスクの期限が前のタスクより前なら、前のタスクの期限と同じ日まで動かす。
- `moveDue` で動かしたタスクの新しい期限（連鎖と引き上げのあとの値）には、次の警告を出す（提案は止めない）。休みの日（`offDayChecker`。土日祝を営業日に数える設定なら、手動の休みだけ）、今日より前、前のタスク（動かしていないもの・完了していないもの）の期限より前。動かした前のタスクより前になるときは、警告ではなく、前のタスクの期限まで引き上げる（上の「前のタスクを足したとき」と同じ規則）。次のタスクなど、連鎖で動いたほかのタスクの期限には、この警告を出さない。
- `addTask` には、文字列の配列 `checklist`（空文字は除く）を付けられ、反映するときに `c1` から採番する。`predecessors` と `moveDue` の `taskId` には、同じ依頼の `addTask` の `ref` を書ける。
- 承認時の `stale` の判定は 1 つ: いまのデータで操作をもう一度計算し（`simulate`）、変更案の表の同一性（`sectionsKey`。期限の行は ID・旧い期限・新しい期限、登録の行は `ref`・件名・プロジェクト・大項目・中項目・期限・前のタスク・項目の文言。開始日の既定と理由の文は含めない）が提案と違う、または計算できない（タスクやプロジェクトが消えた、完了した、など）ときは `stale`。触るタスクの値（`base`）との二重の比較はしない（表の比較で足りる）。保存済みの提案に `base` が残っていても、読まない。
- 保存済みの提案の `ops` に、`PROPOSE_OPS` 以外の操作（`OP_KINDS` のうち、画面で行う操作の名前）が残っていたら、承認は `stale` と同じ扱いで失敗にする（メッセージは「この操作は依頼では受けられません: <op>（画面で行ってください）」）。`propose` も同じ検査で拒否する。保存済みのデータの検証（`validate`）は、`OP_KINDS`（17 種類）を受けるので、古い依頼が残っていても保存できる。
- `--cause` は提案全体で 1 つ。原因が複数あるときは「その他」。
- 開始日のあるタスクに前のタスクを足しても、開始日は変えない（警告も出さない）。
- 提案のあとにデータが変わったときは、反映せず、依頼が「失敗」になる。「もう一度提案してもらう」で作り直す。先に Claude Code の画面で承認・却下した依頼を、HTML でもう一度承認しても、何も変わらない（二重には反映されない）。
- 期限を動かす `moveDue` と、`businessDays` 指定の `addTask` は、同じ依頼にできない。`planOps` が例外を投げる（前のタスクの期限が動くと、営業日が吸収されるため）。`agents/inbox.md` は、期限の移動だけを提案し、登録は承認後にもう一度依頼してもらう。`moveDue` と `due`（日付）指定の `addTask` は一緒にできる。

### 登録（`addTask`）の期限

- `due`（日付）か `businessDays`（営業日の整数）のどちらか一方。`businessDays` は 3650 日（約 10 年）まで（`dueAfter` が 1 日ずつ数えるので、打ち間違いで止まらないようにする）。
- `businessDays` は、完了していない前のタスクの期限の最大値（無ければ今日）から数えて、土日と休みを除いた日数後の日付になる。計算は `core/dates.js` の `dueAfter(base, businessDays, cal)`。
  - `cal` は `core/holidays.js` の `calendarOf(settings)`（`{off, on}`）。
  - `on`（`workdays`）の日は営業日、`off`（`holidays` と `nationalHolidays`）と土日は飛ばす。`on` が最優先。
  - `settings.countWeekendsAndHolidays` が `true` のときは、`calendarOf` が `off` を `holidays` だけにし、`countWeekends: true` を足す。`dueAfter` は `countWeekends` が `true` なら土日を飛ばさない。
- 営業日の計算は受信箱の登録だけで、期限の移動（`moveDue`）とドラッグの期限変更は暦日のまま。
- `propose` が `businessDays` を `due` に置き換えて提案の `ops` に保存するので、承認が翌日以降でも `stale` にならない（提案の表の `add` 行には `businessDays` が残る）。
- HTML の提案カードの登録の表には、行番号（`data-row`）と営業日の列が出る。「修正を依頼する」は暖色（`btn warm`）。

### 見張りと競合

- `tools/inbox.js submit ... --working` は、依頼を `working`（処理中）で作る。`wait` は `pending` だけを知らせるので、`/project-lens:watch` が動いていても `inbox` エージェントに横取りされない。
- `/project-lens:watch` は、Claude Code の Monitor で `node tools/inbox.js wait` を動かす。30 分ごとに終わるので、そのたびに再起動する。見張りが止まると、90 秒ほどで、帯が「見ていません」になる。見ている印（`inbox.watching.at`）が未来の時刻のときは、時計のずれとして 5 分先までだけ許す（それより先の印で、いつまでも「見ています」にならないように）。
  - 止めるときは、この会話で Monitor を起動したときに返ったタスク ID（張り直しと、見張りを何度か始めたときの分を含む、すべて）を `TaskStop` に渡し、以後は届いた依頼を処理しない。ID は、見張りの開始と張り直しの報告に出す（会話が圧縮されても、記録に残りやすくするため）。ID が分からないときは、止めたと記録し、終わりの通知が来ても張り直さず、届いた依頼も処理しない（見ている印は書かれ続けるので、HTML の帯は最長 30 分「見ています」のまま）。スキルの手順としての停止は、未確認（ID を渡して Monitor が止まることだけを確かめた）。
  - 作業中の Claude Code が、依頼のイベントを受け取って動くことは確認済み。
  - Claude Code が入力待ちの間に自動で起きることは、未確認。確認できないときは、作業中の Claude Code に「届いている依頼を処理して」と頼む（手動の入口のコマンドはない）。
- `wait` は、始めるときに `data.json` を 1 回読み、読めない（パスの打ち間違い・壊れた JSON）なら、理由を標準エラーに出して終了コード 1 で終わる。`--timeout` が 0 以上の数、`--interval` が 0 より大きい数でなければ、終了コード 2。始めたあとに読めなくなった回は、確認を飛ばすが、`--timeout` の判定は行う（読めないだけで、終わらなくならないように）。
- `wait` が出すイベント（標準出力）は `request` と `end` だけ。見ている印を書けないとき（`data.json` が検証に通らない、など）は、標準エラーに `見張りの印を書けませんでした: <理由>` を 1 行出し（同じ理由は続けて出さない。書けた回で、いったんリセットする）、次の回にもう一度書く。見張りと依頼の検出は止めない。未確認: Monitor が標準エラーを会話へ出すか（出なければ、利用者は、見張りの出力を見る場合にだけ気づく）。HTML で承認・却下されたことは、知らせない（利用者は HTML で見ている）。見送った理由: 知らせても利用者の操作が要らず、帯の「見ていません」と、画面を開いたときに出るバナー（`validate` の注意）が原因を示す。
- 保存の競合: Claude Code が、受信箱や見ている印（30 秒ごとに更新）を書くので、画面での編集と、ファイルの更新が重なることがある。そのときは、画面が最新のファイルを読み直して、同じ編集を当ててから、もう一度保存する（編集は消えない）。
